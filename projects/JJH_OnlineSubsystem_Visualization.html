KINGSEJONG Session Architecture 프로젝트 상세로 돌아가기

멀티플레이 세션 시스템 책임 구조

이 페이지는 KINGSEJONG의 로비에서 방을 만들고, 검색하고, 참가한 뒤 실제 게임 맵으로 이동하는 과정을 UI, GameInstance, Online Session, Travel, Running Game의 책임으로 나누어 설명합니다.

왜 이렇게 나누었나

Unreal 멀티플레이에서는 세션 생성, 온라인 백엔드 등록, 실제 맵 이동, 게임 진행이 서로 다른 책임입니다. 이를 분리하면 포트폴리오에서 구현 범위와 설계 의도를 더 명확하게 보여줄 수 있습니다.

UI

역할
사용자 입력을 받는 계층입니다.
담당
방 만들기, 방 찾기, 참가 버튼, 검색 결과 슬롯 표시
분리 이유
UI가 세션을 직접 만들면 화면 구조 변경이 네트워크 로직에 영향을 줍니다.

GameInstance

역할
프로젝트가 직접 소유한 세션 관리 계층입니다.
담당
CreateSession, FindSessions, JoinSession, DestroySession
분리 이유
맵 이동 후에도 유지되므로 로비와 게임 맵 사이의 세션 상태를 관리하기 좋습니다.

Online Session

역할
Unreal OnlineSubsystem이 제공하는 실제 세션 데이터 계층입니다.
담당
세션 설정, Presence, 세션 광고 설정값, Steam/LAN 검색 결과
분리 이유
내 코드의 상태와 Steam/LAN 백엔드가 관리하는 데이터를 구분해야 흐름이 명확해집니다.

Travel

역할
세션 참가 이후 실제 맵으로 이동하는 단계입니다.
담당
호스트 ServerTravel, 클라이언트 ClientTravel
분리 이유
세션에 참가했다는 것과 게임 맵에 들어갔다는 것은 Unreal에서 별개의 단계입니다.

Running Game

역할
게임 맵 입장 이후의 서버 권한 게임 진행 계층입니다.
담당
GameMode 판정, PlayerController RPC, Character 동기화
분리 이유
세션 진입 로직과 인게임 규칙을 섞지 않아야 게임 모드 확장이 쉬워집니다.
1. UI 요청플레이어가 방 만들기, 검색, 참가를 누릅니다.
2. GameInstance 처리요청을 세션 함수 호출과 콜백 처리로 바꿉니다.
3. Online Session 반영Steam 또는 LAN 세션에 방 정보가 생성되거나 검색됩니다.
4. Travel 실행호스트와 클라이언트가 각자 다른 이동 함수를 탑니다.
5. 게임 진행GameMode와 RPC 흐름으로 미니게임을 동기화합니다.
핵심은 UI, 세션 관리, 온라인 백엔드 데이터, 맵 이동, 인게임 진행을 한 덩어리로 보지 않는 것입니다. 특히 JoinSession 성공은 접속 주소를 얻는 단계이고, 실제 게임 입장은 ClientTravel까지 완료되어야 합니다.

전체 아키텍처 흐름

각 열은 클래스 종류가 아니라 런타임에서 책임이 넘어가는 구간을 의미합니다. 왼쪽에서 오른쪽으로 사용자의 요청이 실제 게임 입장과 진행으로 바뀝니다.

호스트와 클라이언트 흐름 비교

같은 로비 버튼에서 시작해도 호스트와 클라이언트는 세션 처리와 맵 이동 방식이 다릅니다. 이 차이를 분리해서 보여주는 것이 Travel을 별도 책임으로 둔 가장 큰 이유입니다.

단계 호스트 클라이언트 담당 책임
입력 방 이름, 인원, 카테고리 입력 후 방 만들기 방 찾기 후 검색 결과에서 방 선택 UI
세션 호출 CreateSession 호출 FindSessions, JoinSession 호출 GameInstance
온라인 데이터 세션 설정과 세션 광고 설정값을 Steam/LAN에 등록 Presence 조건으로 검색하고 선택한 결과를 사용 Online Session
맵 이동 ServerTravel("RunningMap?listen") ClientTravel(ResolvedConnectString) Travel
게임 시작 GameMode가 PostLogin과 필요 인원 도달 여부 확인 PlayerController를 통해 UI와 입력 권한을 받음 Running Game

클래스 매핑

포트폴리오 설명에서는 책임 단위로 보여주고, 실제 구현에서는 아래 클래스들이 각 책임을 담당합니다.

책임 대표 클래스 / API 구현 내용
UI ULobbyWidget, 방 슬롯 위젯 사용자 입력을 받고 검색 결과를 표시합니다. 세션 로직은 직접 수행하지 않고 GameInstance의 인터페이스를 호출합니다.
GameInstance UJJH_GameInstance 세션 인터페이스 보관, 완료 델리게이트 등록, 생성/검색/참가/파괴 함수를 관리합니다.
Online Session IOnlineSessionInterface, FOnlineSessionSettings Steam 또는 LAN 세션에 저장되는 Presence, Lobby, 세션 광고 설정값, 검색 결과를 다룹니다.
Travel ServerTravel, ClientTravel 세션 생성 또는 참가 이후 실제 게임 맵으로 이동합니다. 호스트와 클라이언트가 서로 다른 경로를 사용합니다.
Running Game RunningGameModeBase, RunnerController, RunnerCharacter 게임 시작 조건, 퀴즈 선택, 정답 판정, 입력 제어, 캐릭터 동기화를 서버 권한 기준으로 처리합니다.

구현 포인트

이 구조를 통해 강조할 수 있는 기술적 결정입니다.

GameInstance에 세션 집중

  • 맵 이동 후에도 유지되는 객체에 세션 상태와 콜백을 모았습니다.
  • UI는 버튼 입력과 표시만 담당해 화면 변경 비용을 줄였습니다.
  • 세션 종료와 네트워크 실패 복구를 로비 복귀 흐름으로 통일했습니다.

세션 데이터와 UI 데이터 분리

  • Online Session Settings의 세션 광고 설정값을 FRoomInfo로 변환했습니다.
  • 방 이름, 카테고리, 인원, 핑을 UI가 쓰기 쉬운 형태로 정리했습니다.
  • 한글 방 이름 저장을 위해 Base64 인코딩과 디코딩을 적용했습니다.

세션 이후는 서버 권한

  • 정답 판정, 입장 순서, 게임 종료 판단은 서버 GameMode에서 처리했습니다.
  • 개별 UI는 Client RPC, 공통 연출은 Multicast RPC로 분리했습니다.
  • 세션 진입 로직과 인게임 규칙을 분리해 미니게임 확장에 대응했습니다.
