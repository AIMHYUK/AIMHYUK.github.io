만든 이유 데이터 흐름 파싱 스레드 경계 비교 실험 한계

플러그인이 가려두던 계층을 열어서 직접 재봤습니다.

Stage On에서 RPC 대신 UDP/OSC를 택한 판단이 실제로 유효했는지, 2년 뒤 소켓·수신 스레드·바이트 파싱을 직접 구현하고 같은 데이터를 양쪽 경로로 보내 비교했습니다. 결과보다 무엇을 재야 하는지를 세 번 고쳐 잡은 과정이 이 프로젝트의 내용입니다.

만든 이유

Stage On에서 내린 구조 선택의 근거가 내 손에 없었습니다.

출발점

Stage On에서는 일정상 VRM4U → UOSCServer 플러그인으로 OSC를 받았습니다. 구조 선택과 연결은 제가 했지만 소켓 생성, 수신 스레드, 바이트 파싱은 전부 플러그인이 처리했습니다. "왜 RPC가 아니라 OSC였나"를 설명할 때 제가 실제로 확인한 것은 증상뿐이었습니다.

확인하려던 것

"RPC가 느리다"가 아닙니다. 그건 부정확한 주장입니다. 확인하려던 것은 고빈도 외부 데이터에 엔진 네트워킹 경로가 구조적으로 맞지 않는가였습니다.

만든 것

플러그인 없이 FUdpSocketBuilder부터 OSC 바이트 파서까지 직접 구현하고, 같은 궤도 데이터를 RPC로도 보내는 비교군(RpcMotionActor)을 함께 만들었습니다.

데이터 흐름

파이썬이 보낸 실수 1.5가 큐브의 위치가 되기까지 8단계를 거칩니다.

  • ② 커널 버퍼 — WithReceiveBufferSize를 1MB로 잡았습니다. 이 값이 작으면 꺼내가기 전에 버퍼가 차서 커널이 조용히 버리고, UDP는 재전송이 없어 그대로 유실입니다.
  • ③ 왜 별도 스레드인가 — 게임 스레드에서 소켓을 읽으면 프레임당 한 번(≈16ms)만 확인하게 되어 그 사이 도착한 패킷이 쌓이다 넘칩니다. 폴링을 1ms로 잡으면 60~120Hz 스트림을 놓치지 않으면서 CPU 부하도 크지 않습니다.
  • ⑧ 주소 분기 — 같은 포트, 같은 소켓으로 들어온 데이터를 주소 패턴만으로 다른 처리로 보냅니다. 위치는 Transform에, 페이셜은 로그로. 실제 모션캡처에서 본 데이터와 표정 데이터를 분리하는 것과 같은 구조입니다.

바이트 파싱 — 걸린 지점 셋

플러그인이 감춰두던 부분이자, 이 프로젝트를 만든 이유입니다.

① 4바이트 정렬

/cube/pos는 9글자지만 12바이트를 소비합니다. 널 포함 10을 4의 배수로 올림하기 때문입니다. (n + 3) & ~3 — 하위 2비트를 버리면 4의 배수가 되므로 먼저 3을 더해 올림 효과를 냅니다.

② 빅엔디안

OSC는 네트워크 바이트 오더를 씁니다. x86은 리틀엔디안이라 그대로 복사하면 값이 뒤집힙니다. 가장 앞 바이트를 최상위로 두고 << 24부터 조립했습니다.

③ float는 변환이 아니라 재해석

가장 헷갈린 부분입니다. 3f c0 00 00을 조립하면 정수 0x3FC00000이 나오는데, 여기서 (float) 캐스팅하면 약 10억이 됩니다. 원하는 건 값 변환이 아니라 같은 32비트를 IEEE754로 다시 읽는 것이고, 그 결과가 1.5입니다.

// 값을 바꾸는 게 아니라 비트를 그대로 다시 읽는다.
// reinterpret_cast도 되지만 strict aliasing 위반 소지가 있어 Memcpy를 썼다.
FMemory::Memcpy(&OutValue, &AsInt, sizeof(float));

// 매 읽기마다 경계 검사 — 없으면 잘린 패킷 하나로 버퍼 오버리드
if (InOutOffset + 4 > Size) return false;
  • 알 수 없는 타입 태그를 만나면 즉시 실패시킵니다. 크기를 모르면 이후 오프셋 전체를 신뢰할 수 없어, 계속 읽으면 쓰레기 값이 나옵니다.
  • 네트워크로 들어오는 데이터는 신뢰할 수 없다는 전제로, 파싱에 성공했더라도 Floats.Num() >= 3처럼 기대한 형태인지를 따로 확인합니다.

스레드 경계

수신 콜백은 게임 스레드가 아닙니다. 이 프로젝트에서 가장 중요한 지점입니다.

왜 액터를 만지면 안 되는가

언리얼의 UObject는 스레드 세이프하지 않습니다. 게임 스레드가 Tick을 도는 중에 다른 스레드가 Transform을 쓰면 값이 절반만 갱신되는 데이터 레이스가 되고, GC가 객체를 정리하는 타이밍과 겹치면 해제된 메모리 접근으로 크래시합니다.

// 수신 스레드 — 계측 카운터조차 원자적으로.
// ++ 는 "읽고-더하고-쓰는" 세 동작이라 중간에 끼어들면 값이 어긋난다.
FPlatformAtomics::InterlockedIncrement(&TotalPacketsReceived);

// 생산자 1(수신 스레드) · 소비자 1(게임 스레드)로 확정되어 있어 락이 필요 없다
TQueue<FOscMessage, EQueueMode::Spsc> MessageQueue;
MessageQueue.Enqueue(MoveTemp(Message));   // TArray 복사도 피한다

왜 락을 피했는가

수신 스레드가 락을 기다리며 멈추면 그동안 소켓을 읽지 못하고, 커널 버퍼가 차서 패킷이 유실됩니다. 수신 경로에서 대기를 없애는 것이 유실 방지에 직결됩니다.

종료 순서

Receiver->Stop()으로 스레드를 먼저 멈추고 그다음 소켓을 닫습니다. 반대로 하면 아직 돌고 있는 스레드가 해제된 소켓을 건드려 크래시합니다. 소켓은 delete가 아니라 서브시스템에 DestroySocket으로 반납합니다 — 내가 new한 자원이 아니기 때문입니다.

비교 실험

같은 궤도 데이터를 RPC 경로로도 보내 조건을 맞춰 비교했습니다.

공정성을 위해 통제한 것

조건을 맞추지 않으면 사과와 오렌지를 재게 됩니다. 같은 계측기(양쪽 다 UReceiveStatsComponent), 같은 궤도(ComputeLocation()이 send_osc.py와 동일한 식), 자동 복제 차단(SetReplicateMovement(false) — 안 하면 RPC와 무관하게 큐브가 움직여 측정이 오염됩니다), 서버 자기 호출 제외(HasAuthority()면 계측하지 않음 — Multicast는 서버에서도 즉시 실행되어 항상 100%로 보입니다). 뒤의 둘을 빠뜨리면 결과가 통째로 무의미해집니다.

Reliable RPC — 하드 실패

순서 보장을 위해 전송 버퍼에 쌓아두는데, 소비보다 생산이 빠르면 버퍼가 넘칩니다. 언리얼은 데이터 무결성을 지킬 수 없다고 판단해 연결을 종료합니다. 느려지는 게 아니라 복구 방법이 없습니다.

Unreliable RPC — 버티지만 못 받는다

연결은 유지됩니다. 대신 12,000개 중 79개만 도착하고(0.66%) 유실이 36만 건까지 누적됩니다. "끊기지 않는다"와 "동작한다"는 다릅니다.

OSC — 다 받지만 대가가 있다

유실은 0이지만 초기 FPS가 3까지 떨어졌다 60으로 회복합니다. 지연 누적을 막으려고 큐를 전부 비우게 했는데, 초당 24,000개가 들어오니 한 프레임에 8,000개를 처리한 탓입니다.

결론 — 세 방식은 실패하는 모양이 다르다

Reliable RPC는 무결성을 못 지키겠다며 연결을 끊고(복구 불가), Unreliable RPC는 연결은 유지한 채 99.4%를 버리고, OSC는 다 받는 대신 게임 스레드가 부담을 집니다. 셋 중 OSC만 "내가 제어할 수 있는 실패"입니다 — 앞의 둘은 엔진이 알아서 끊거나 버리지만 OSC는 처리 정책을 직접 정할 수 있습니다. 이것이 고빈도 외부 데이터 수신에서 OSC를 택하는 구조적 이유입니다.

여기에 더해, 애초에 RPC로는 외부 프로그램의 데이터를 직접 받을 수 없습니다. RPC는 언리얼 네트워크 세션에 참여한 노드끼리만 주고받으므로, 모션캡처 앱의 데이터를 RPC로 받으려면 일단 서버로 들여오는 중계 계층이 반드시 한 겹 필요합니다. OSC는 그 계층을 통째로 없앱니다. 성능 이전에 아키텍처가 맞지 않았습니다.

한계와 배운 것

반드시 함께 말해야 하는 부분입니다.

이 수치를 어떻게 쓸 것인가

이것은 직접 만든 데모 환경에서 측정한 값이지 Stage On의 실제 수치가 아닙니다. Stage On은 환경도 데이터도 다르고 그 수치는 관측한 적이 없으므로 쓰지 않습니다. 이 실험의 가치는 과거 수치를 사후에 정당화하는 데 있지 않고, 왜 그 구조가 맞지 않았는지를 직접 확인했다는 데 있습니다.

  • PIE의 리슨 서버는 클라이언트와 같은 프로세스입니다. 실제 소켓 지연·손실을 겪지 않습니다.
  • NetServerMaxTickRate 조작이 PIE에서 적용되지 않아, 틱레이트의 영향은 검증하지 못했습니다.
  • 본 데이터가 위치(float 3개)뿐입니다. 실제로는 회전까지 있어 페이로드가 더 큽니다.
  • 저부하에서는 아무 차이도 관측되지 않았습니다. 차이는 실제 모션캡처 수준의 부하에서만 드러났습니다.
  • 현재 OSC 구현은 "전부 처리"를 택했고 그 대가가 프레임레이트로 나타났습니다. 모션 데이터는 최신 값만 의미가 있으므로, 주소별 최신 값만 남기고 폐기하는 편이 맞습니다. 미개선 상태입니다.

무엇을 재야 하는지가 절반이었다

처음 지표(초당 수신 개수)로는 두 경로가 똑같아 보였습니다. 지표를 세 번 바꾸고(개수 → 버스트 → FPS 대조) 부하를 올린 뒤에야 진짜 차이가 드러났습니다.

"끊김"의 정체

Reliable RPC는 개수를 보장합니다. 틱레이트는 전송 빈도를 제한할 뿐 메시지를 버리지 않습니다. 대신 한 틱에 4개씩 묶여 오고, 한 프레임에 4개를 적용해도 화면에 남는 건 마지막 값 하나입니다. 초당 개수가 같아도 눈에 보이는 갱신은 1/4이 됩니다.

유실 0이 항상 좋은 것은 아니다

모션 데이터는 최신 값만 의미가 있어 한 프레임 빠져도 다음이 덮어씁니다. 반대로 Reliable로 재전송하면 이미 지나간 자세를 받느라 최신 자세가 밀립니다. 유실 허용이 오히려 이 데이터에 맞는 선택입니다.
