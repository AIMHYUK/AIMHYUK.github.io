버튜버 모션 데이터를 실시간으로 받아 무대에 반영하는 공연 플랫폼입니다. 무대 프리셋 선택 UI, StreamLevel 기반 무대 교체, Actor Tag 기반 오브젝트 정리, SceneCapture 썸네일 생성, OSC 수신 흐름 정리를 맡았습니다. 구현은 Blueprint 중심이며 일부를 C++로 작성했습니다.

문제와 선택

모션 데이터를 본 단위로 RPC 전달하던 구조는 본 개수만큼 호출이 늘어 실시간 전송을 따라가지 못했습니다. UDP 기반 OSC 수신으로 전환해 외부 모션캡처 데이터를 직접 받도록 바꿨습니다.

성과와 검증

과학기술정보통신부 장관상 수상작. 무대 구성, 아바타 적용, OSC 수신, HTTP 업로드까지 하나의 시연 흐름으로 연결했습니다.

  • Sky / Theme / Floor / VFX 카테고리를 조합하는 무대 구성 시스템과 설정 UI를 제작했습니다.
  • StreamLevel 동적 로드·언로드와 Actor Tag 기반 정리 로직으로, 아트 리소스가 늦게 들어와도 코드 수정 없이 반영되게 했습니다.
  • SceneCaptureComponent2D와 RenderTarget으로 현재 카메라 시점 썸네일을 생성하고, HTTP Multipart 업로드 응답 URL을 무대 저장에 연결했습니다.
  • 당시 OSC 수신은 VRM4U와 UOSCServer 플러그인을 사용했습니다. 그 내부가 어떻게 동작하는지, 그리고 이 전환이 실제로 유효했는지는 아래에서 비교 실험을 설계해 측정했습니다.

MiniOscReceiver

2026.07 · 개인 프로젝트
Unreal Engine 5.6 C++ UDP Socket Lock-free Queue
동기

Stage On에서 쓴 OSC 수신은 VRM4U → UOSCServer 두 겹에 소켓, 스레드, 파싱이 가려져 있었습니다. 플러그인이 대신 해주던 일을 계층별로 열어보고, 당시의 RPC → OSC 전환이 실제로 유효했는지 측정하려고 만들었습니다.

열어본 계층

FUdpSocketBuilder 소켓 생성 → FUdpSocketReceiver 수신 스레드 → OSC 바이트 직접 파싱 → SPSC 락프리 큐로 게임 스레드 마샬링

결론이 뒤집힌 지점

본 1개의 저부하에서는 세 방식 모두 차이가 없었습니다. 거기서 멈췄다면 “차이 없음”이라는 반대 결론을 낼 뻔했습니다.

  • 파싱에서 걸린 지점 세 가지: 4바이트 정렬 (n+3)&~3, 빅엔디안 조립, float는 캐스팅이 아니라 Memcpy 비트 재해석.
  • 수신 스레드가 액터를 직접 건드리지 않도록 SPSC 락프리 큐로 넘기고, 게임 스레드에서 꺼내 Transform에 반영했습니다.
  • 한계도 함께 남겼습니다. OSC도 큐를 전부 비우는 설계 탓에 초기 프레임레이트가 떨어졌고(프레임당 상한 또는 최신 값만 유지로 개선 가능), PIE 리슨서버라 실제 네트워크 지연은 없는 조건이었습니다.

패턴은 요구사항에서

유물 52종을 얹을 때 데코레이터가 첫 발상이었지만 기각했습니다. 이유는 구식이라서가 아니라 획득 순서가 매 판 랜덤이라는 게임 규칙 때문입니다 — 체인은 감싼 순서가 곧 연산 순서라 같은 조합을 든 두 플레이어의 수치가 달라집니다. 애그리게이터로 통합했습니다.

  • 엔진과 싸우지 않되, 어디까지 위임할지는 실측으로 정했습니다. 커스텀 이동을 직접 굴리다 애니메이션과 접지가 계속 깨져 엔진 기본 지상 물리로 되돌리니 세 문제가 한 번에 풀렸고, 반대로 넉백은 엔진 물리로 갔다가 되돌아왔습니다 — 그쪽은 권위 모델이 맞지 않았습니다.
  • 1511줄까지 자란 서버 컨트롤러를 셋으로 분리하고, 같은 파일을 만지게 된 시점에 API 계약 문서를 먼저 쓰고 경계를 다시 세웠습니다. 그 전까지는 폴더로 완전히 분리해 작업해 PR 머지 시 충돌 0건이었습니다.
  • “동작한다”를 두 층으로 나눠 묻게 됐습니다. 훅 핸들러 다섯 개가 직접 호출하면 정상 동작하는데 실전에서는 한 번도 불리지 않고 있었습니다 — 코드가 갈라지는 축(서버/클라 · 근접/원거리)에서 한쪽 분기에만 호출부를 둔 탓이고, 게임을 띄우기 전 grep 한 번으로 보였을 문제였습니다.
  • 검증은 Maker MCP로 에디터를 자동 조작해 측정했습니다(refresh → play → 서버 컨텍스트에 Lua 주입 → 로그 수집 → stop). 런타임 주장에는 실행 결과를 붙이고, 멀티플레이 기능은 원격 대상으로 측정합니다 — 개발 환경은 서버와 클라가 한 프로세스에 떠서 권위 문제를 가립니다.
  • 밸런스 수치의 내적 모순을 발견했을 때는 임의로 고치지 않고 선택지 세 개와 각각의 대가를 정리해 결정을 요청했고, 유물 중첩을 가산으로 할지 곱으로 할지 같은 구조 결정은 근거를 명시하고 직접 정했습니다.

기술 구현 요약

프로젝트에서 직접 다룬 기능과, 구현 과정에서 어떤 기준으로 설계 결정을 했는지 정리했습니다.

기술구현 내용설계 기준
UDP / OSC 소켓 생성, 수신 스레드, OSC 바이트 파싱(4바이트 정렬, 빅엔디안, 비트 재해석), SPSC 락프리 큐 마샬링 수신 스레드가 게임 오브젝트를 직접 건드리지 않도록 큐 하나로 경계를 만들고, 부하를 바꿔가며 RPC와 비교 측정했습니다.
Realtime Sync 본 단위 RPC 전달을 UDP/OSC 수신으로 전환, 모션과 페이셜을 주소(Path)별로 분리 처리 본 개수에 비례해 호출이 늘어나는 구조를 데이터 스트림 수신으로 바꿔, 전송 횟수가 아니라 최신성을 기준으로 삼았습니다.
Optimization 프로파일러로 Instantiate/Destroy 반복에 따른 GC 부하 특정, 오브젝트 풀링 도입 추측으로 고치지 않고 원인을 먼저 측정으로 확인한 뒤, 생성과 파괴 자체를 없애는 쪽으로 구조를 바꿨습니다.
OnlineSubsystem 세션 생성, 검색, 참가, 종료, Subsystem 기준 LAN/Steam 판정, 세션 광고 설정값 등록 비동기 Delegate 완료 시점 기준으로 UI 상태, 실패 처리, Delegate 정리를 함께 관리했습니다.
