어떤 게임인가

캐릭터는 스스로 전진하고, 마주치면 무기 가중치로 밀고 밀리며 자동으로 공격을 주고받습니다. 플레이어가 개입하는 것은 직업 고유 스킬 · 대시 · 방향 전환 세 가지뿐입니다.

“조작을 줄이면 무엇으로 이기는가”가 설계의 중심 질문이었습니다. 답은 무기와 직업의 조합, 그리고 세 개입의 타이밍입니다. 그래서 전투의 모든 수치가 데이터로 빠져 있고, 판정은 프레임 단위로 정의됩니다.

넥슨 글로벌 개발 콘테스트 출품 예정(10/7 마감). 진행 중인 프로젝트입니다.

촬영 필요 — 대표 화면

자동 전투가 벌어지는 아레나 화면. 여러 캐릭터가 붙어 있고 체력·유물 UI가 보이면 “무슨 게임인지”가 한 장으로 전달됩니다. MSW Maker의 Play 화면을 캡처하면 됩니다.

기능 01

타격 판정을 “닿는 순간”으로

공격하는 일과 맞는 일을 분리했더니 회피가 성립했습니다.

구현

  • 한 함수였던 공격을 둘로 갈랐습니다 — AutoAttack은 쿨 소모와 스윙 모션만(적이 있든 없든 실행), ResolveHit은 impactDelay 뒤의 판정.
  • 무기마다 WeaponData.impactDelay를 뒀습니다 — 주먹 0.10 / 대검·둔기 0.22 / 활 0.18.
  • ResolveHit은 그 시점의 위치와 방향으로 대상을 다시 찾습니다. 스윙 시작 때 찾아둔 대상을 기억하지 않습니다.

화면

촬영 권장 — 사진 1 · 스윙 시작

공격 모션이 시작되는 프레임. 아직 체력이 깎이지 않은 상태.

촬영 권장 — 사진 2 · 대시로 회피

스윙 도중 대시로 빠져나가 맞지 않는 순간. 이 기능이 만든 게임성이 눈에 보이는 유일한 장면입니다.

어려움

문제
주먹이나 검이 아직 닿지도 않았는데 숫자가 먼저 내려갔습니다. 스윙 시작 프레임에 체력이 깎여 눈에 띄게 어색했습니다.
원인
구조 문제였습니다. “공격한다”와 “맞는다”가 한 함수였습니다. 쿨 확인 → 대상 찾기 → 데미지 → 모션 재생이 한 줄로 이어져 있었습니다.
해결
둘을 분리하고, 판정 시점에 대상을 다시 찾도록 했습니다. 그러자 스윙 도중 대시나 방향 전환으로 빠져나가면 안 맞습니다. 근접전에서 회피가 성립하게 됐고, 플레이어의 세 개입 중 둘이 여기서 의미를 갖습니다. 판정이 닿는 순간으로 옮겨졌으므로 피격 연출의 이중 지연(HitFlashDelay 0.13)도 0으로 내렸습니다.

성과

근접전에서 회피 성립 체력이 깎이는 순간과 연출이 일치
기능 02

105 스윙 실측 — 내 설계를 데이터로 반박

판정을 관대하게 만들려고 넣은 기능이, 재보니 거의 일하지 않고 있었습니다.

구현

  • impactDelay는 한 점이라 그 순간 그 자리에 없으면 무조건 빗나갑니다. 격투게임의 active 프레임처럼 판정이 열려 있는 구간을 줬습니다.
  • WeaponData.activeDuration — 대검 0.18 / 둔기 0.16 / 주먹·표창·스태프·활 0.10 / 단검·너클 0.08 / 권총 0.06. 무거울수록 관대, 빠를수록 좁게가 배분 규칙이고, 전부 impactDelay + activeDuration < attackInterval 안에 들어갑니다.
  • 다단히트가 아닙니다 — 적중하면 구간을 즉시 닫습니다. 안 닫으면 한 스윙이 10회 이상 때립니다. 다음 공격이 시작되면 이전 구간을 강제 종료합니다.

화면

어려움

문제
판정을 관대하게 만들려고 제가 직접 도입한 active 구간이, 실측해보니 기여도 3%였습니다. 넣을 가치가 있었는지 자체가 의심스러워졌습니다.
원인
적중 3건이 모두 구간 앞 0.05초 안에 잡혔습니다(경과 0.016 / 0.048 / 0.048). 대검의 0.18초 중 뒤 0.132초는 한 번도 일하지 않았습니다. 원리로도 맞습니다. 구간이 건지는 상황은 사거리를 살짝 벗어난 상대가 걸어 들어오는 경우인데, 이동 속도가 2~3 유닛/초면 0.05초에 0.1~0.15 유닛밖에 못 좁힙니다.
해결
구간을 실제로 일하는 길이로 줄였습니다. 그리고 제가 만든 기능이 근거가 약하다는 결론을 커밋 메시지에 그대로 남겼습니다. 여기서 얻은 것은 수치보다, 만든 사람이 자기 기능의 효과를 재는 습관입니다.

성과

기여도 3% · 뒤쪽 73% 미사용을 수치로 확인 로그 정합성 검증 후에 결론 다단히트 0건
기능 03

서버 권위 일원화

같은 값이 두 벌로 갈라진 사건 이후의 원칙입니다.

구현

  • 클라이언트가 구동하던 이동 드라이버 스택을 4단계에 걸쳐 은퇴시키고 서버 컨트롤러로 통합했습니다. 한 번에 걷어내지 않은 것은 되돌릴 여지를 남기기 위해서입니다.
  • 커스텀 이동을 직접 굴리다 애니메이션과 접지가 계속 깨져 엔진 기본 지상 물리로 되돌렸더니 세 문제가 한 번에 풀렸습니다.
  • 반대로 넉백은 엔진 물리로 갔다가 되돌아왔습니다. 물리 권위가 클라이언트에 있는 환경이라 위치 판정을 서버가 쥘 수 없었습니다. 결정론적 공식으로 회수했습니다.

화면

촬영 권장 — 권위 불일치 로그

서버와 클라이언트의 HP가 갈라진 로그(786 vs 1000)가 남아 있으면 이 항목의 출발점이 그대로 보입니다. 없으면 이 칸은 비워도 됩니다.

어려움

문제
HP가 서버와 클라이언트 두 벌로 갈라져 786과 1000으로 어긋났습니다. 어느 쪽이 진짜인지 코드만 봐서는 알 수 없었습니다.
원인
값의 주인을 정하지 않고 양쪽에서 갱신하고 있었습니다. 이동도 마찬가지로 클라 구동 드라이버와 서버 로직이 겹쳐 있었습니다.
해결
이후로는 “이 값의 주인이 누구인가”를 매번 먼저 정하고 시작했습니다. 다만 엔진에 위임할 것과 직접 할 것은 감이 아니라 실측으로 갈랐습니다 — 이동은 엔진에 넘기고, 넉백은 되찾아왔습니다. 같은 원칙이 두 번은 위임으로, 한 번은 회수로 나타났습니다.

성과

이동 드라이버 4단계 은퇴 → 서버 일원화 1511줄 컨트롤러를 셋으로 분리 · API 계약 문서화
기능 04

유물 52종 스탯 파이프라인

패턴을 취향이 아니라 게임 규칙에서 도출한 사례입니다.

구현

  • 로그라이크 성장으로 유물 52종(A 18 · B 18 · C 16)을 얹었습니다.
  • 스탯 경로가 이미 두 갈래인 것을 확인하고, 유물을 세 번째 경로로 만들지 않기로 했습니다. 애그리게이터로 통합했습니다.
  • 치명타·흡혈·방어막·피해 숫자를 신설하고, 임시 라운드 스텁으로 15종을 검증 가능하게 만들었습니다.

화면

촬영 필요 — 유물 선택 화면

라운드 사이에 유물을 고르는 화면. 52종이 있다는 것과 등급(A/B/C) 구분이 보이면 좋습니다.

어려움

문제
유물이 스탯을 고치는 구조를 짜야 하는데, 데코레이터 체인이 첫 발상이었습니다. 각 유물이 앞의 결과를 감싸는 방식입니다.
원인
기각한 이유는 “구식이라서”가 아닙니다. 이 게임은 획득 순서가 매 판 랜덤입니다. 체인은 감싼 순서가 곧 연산 순서라, 같은 유물 조합을 든 두 플레이어의 수치가 달라집니다.
해결
순서에 무관하게 합산되는 애그리게이터로 갔습니다. 요구사항(획득 순서 랜덤)을 먼저 적어두면 패턴은 거기서 나옵니다. 패턴을 고르고 요구사항을 맞추는 순서가 아니었습니다.

성과

유물 52종 · 순서 무관 합산 스탯 경로를 셋으로 늘리지 않음

범위와 한계

4인 팀이며 제 담당은 플레이어 이동·전투·스킬 시스템, 데이터 레이어, 서버 권위 구조입니다. 초기 서버 권위 이동 프로토타입과 플레이어 충돌·애니메이션 동기화는 팀원(PR #1), 스킬 키 UI 그룹은 다른 팀원(PR #2), 매치메이킹은 별도 담당입니다.

진행 중인 프로젝트라 위 수치와 구조는 바뀔 수 있습니다. 측정은 MSW Maker MCP로 에디터를 자동 조작해 수행했고 (refresh → play → 서버 컨텍스트에 Lua 주입 → 로그 수집 → stop), 런타임 주장에는 실행 결과를 붙인다를 원칙으로 삼았습니다.

개선점 하나를 남겨둡니다 — 훅 핸들러 다섯 개가 직접 호출하면 동작하는데 실전에서는 한 번도 불리지 않고 있었습니다. 코드가 갈라지는 축(서버/클라 · 근접/원거리)에서 한쪽 분기에만 호출부를 둔 탓이고, 게임을 띄우기 전 grep 한 번으로 보였을 문제였습니다.
