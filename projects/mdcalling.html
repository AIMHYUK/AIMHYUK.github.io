어떤 게임인가

NPC에게 주문을 받고, 치킨·피자 같은 음식을 가방에 넣어 목적지까지 배달합니다. 가방은 테트리스처럼 칸을 차지하는 격자라, 무엇을 어떻게 넣느냐가 한 번에 받을 수 있는 주문 수를 결정합니다.

제 담당은 가방(인벤토리) 설계와 구현, 대화 시스템 연동과 선택지 UI, 그리고 배달 도메인 재설계입니다.

퀘스트 프레임워크와 마우스·게임패드 입력 체계는 팀원이 설계한 것이며, 저는 그 위에서 확장하는 쪽을 맡았습니다. 기여 범위는 저장소 README에 git blame 기준으로 정리해 두었습니다.

기능 01

테트리스형 그리드 인벤토리와 무게중심

음식마다 차지하는 칸 모양이 다르고 회전해서 끼워 넣습니다. 그리고 짐이 한쪽으로 쏠리면 가방이 실제로 기웁니다.

구현

  • InventoryModel이 2차원 배열로 점유 상태를 관리하고, 변경이 생기면 이벤트만 발행합니다. 뷰는 그 이벤트를 받아 그릴 뿐 모델을 역참조하지 않습니다 — 이벤트 기반 MVC입니다.
  • 배치 가능 여부는 격자 위에서 즉시 표시됩니다(밝은 칸이 놓을 수 있는 자리).
  • 격자에 놓인 아이템의 무게 × (아이템 중심 X − 격자 중심 X)를 전부 더해 토크를 냅니다. 오른쪽에 무거운 걸 몰면 양수, 왼쪽이면 음수입니다. 토크는 아이템을 놓거나 뺄 때만 다시 계산합니다 — 매 프레임 도는 계산이 아닙니다.
  • 모델은 각도를 모릅니다. OnTorqueChanged로 토크 값만 발행하고, 그걸 각도로 바꾸는 일은 InventoryTiltView가 합니다. 기울기 배율과 최대 각도는 인스펙터 값이라 연출만 따로 조정됩니다.
  • 담당 파일 — InventoryModel, InventoryController, InventoryState, InventoryTiltView.

화면

성과

충돌 판정에서 회전 분기 제거 토크 재계산은 배치·제거 시에만 뷰가 모델을 역참조하지 않는 단방향 구조 모델은 각도를 모르고 토크만 발행

이어서

인벤토리 직접 만져보기 실제 RecalculateTorque() 계산식을 그대로 옮긴 시뮬레이터입니다. 아이템을 놓아 보면 토크 값과 기울기가 즉시 바뀝니다. 구조 설명도 같은 페이지에 있습니다.
기능 02

Yarn Spinner 대화 스크립트 연동

대화가 게임 상태를 직접 묻고, 대화 도중 배달 요청 화면으로 빠졌다 돌아옵니다.

구현

  • YarnDialogueManager가 Yarn 커맨드·함수 핸들러를 등록해 .yarn 대화 스크립트와 게임 로직을 잇습니다.
  • 대화가 게임 상태를 직접 물을 수 있도록 [YarnFunction]을 노출했습니다. 덕분에 대화 작가가 <<if has_delivery_for_pickup_location()>> 같은 분기를 코드 수정 없이 스크립트 안에서 쓸 수 있습니다.
  • LocalOptionPresenter로 Yarn 기본 선택지 표시기를 대체했습니다. 선택지를 화면 하단이 아니라 말하는 대상 근처에 띄우고, YarnOptionsAutoFocus가 첫 선택지에 자동으로 포커스를 잡습니다.
  • 타협한 부분 — [YarnFunction]은 Yarn 측 요구로 반드시 static이어야 합니다. 그래서 “지금 대화 중인 장소”를 static 필드로 두고 주입하는 방식을 썼습니다. 전역 상태라 대화가 끝날 때 반드시 되돌려야 다음 대화가 오염되지 않습니다 — 대화가 동시에 두 개 진행되지 않는다는 게임 규칙에 기대고 있는 구현입니다.
  • 담당 파일 — YarnDialogueManager, LocalOptionPresenter, OptionItemPrefab, YarnOptionsAutoFocus.

화면

성과

대화 ↔ 상태 머신 왕복을 코루틴 하나로 대화 스크립트가 게임 상태를 직접 질의 선택지를 말하는 대상 근처에 표시
기능 03

퀘스트 구조 재설계 — 사람이 아니라 장소로

퀘스트를 사람이 아니라 장소에 매달아, 콘텐츠를 늘릴 때마다 NPC를 만들어야 하는 구조를 끊었습니다.

구현

  • 이전에는 대화를 NPC가 소유했습니다. 대화 시작 노드가 NpcController의 데이터에 박혀 있어서, 배달지를 하나 늘리려면 그 대화를 들고 있을 NPC 게임오브젝트를 월드에 새로 배치해야 했습니다.
  • Location을 ScriptableObject로 도입하고, 대화 시작 노드의 소유자를 NPC에서 장소(PlaceInteractable)로 옮겼습니다. 상호작용 대상이 건물 자체가 되고, 등장 인물은 장소 대화 UI의 캐릭터 스프라이트로 그려집니다. 덕분에 한 장소에 여러 인물을 세울 수 있고, NPC 오브젝트를 늘리지 않아도 됩니다.
  • PlaceInteractableManager가 Location → PlaceInteractable 사전을 들고 장소를 조회합니다. NPC 기준 조건 4종을 삭제하고 판정을 장소 기준 질의로 통합했습니다.
  • 진행도에 따라 대화가 바뀌는 것은, QuestAction 확장점에 추가한 제 액션이 그 장소의 yarn 시작 노드를 갈아끼우기 때문입니다. 원래 대화로 되돌리는 defaultYarnStartNode 경로도 함께 뒀습니다.

화면

성과

NPC 종속 조건 4종 제거 팀 프레임워크 수정 0 대화 시작 노드의 소유자를 NPC → 장소로 이전 한 장소에 여러 인물 — NPC 오브젝트 증식 차단 퀘스트 진행도에 따라 장소의 대화 노드 교체

이어서

퀘스트 프레임워크 구조 분석 확장하기 전에 팀 프레임워크를 어디까지 파악했는지 — 계층·상태·보고 흐름 다이어그램으로 정리했습니다. 본인 작성 코드가 아닙니다.

기능 01 — 여러 칸을 차지하는 아이템을 한 장의 스프라이트로 그리기

문제
가방은 고정 크기 셀의 격자인데 아이템은 한 칸이 아니라 EffectiveSize만큼 여러 칸을 차지합니다. 셀마다 스프라이트를 타일링하면 치킨 한 마리가 네 조각으로 잘려 보입니다. 아이템 하나는 몇 칸을 덮든 스프라이트 한 장이어야 했습니다.
원인
격자 UI를 짜면 자연히 아이템 RectTransform을 셀의 자식으로 넣게 됩니다. 그런데 자식이 되는 순간 아이템은 부모 셀의 사각형에 묶여 한 칸 크기를 넘어설 수 없습니다. 부모를 넘어 여러 칸을 덮을 방법이 없었습니다.
해결
아이템 뷰를 셀의 자식이 아니라 격자 루트의 형제로 생성해 (Instantiate(itemPrefab, _rectTransform)) 셀 층 위에 겹쳤습니다.
부모–자식이 아닌데 어떻게 칸에 들어맞는가 — 두 층이 같은 배치 규약을 쓰기 때문입니다. 셀도 아이템도 anchorMin·anchorMax·pivot = Vector2.up(좌상단)으로 두고, anchoredPosition = (x, −y) × TotalCellSize라는 동일한 식으로 자리를 잡습니다. 다른 것은 sizeDelta뿐이라 계층 관계 없이도 정확히 겹칩니다.
좌표계
그리드는 y가 아래로 증가하고 유니티 UI 로컬 좌표는 위로 증가합니다. 그려 넣을 때 anchoredPosition에서 −y로 뒤집고, 화면 좌표를 셀로 역변환할 때도 같은 부호 처리를 합니다 — ScreenPointToLocalPointInRectangle으로 로컬 좌표를 얻은 뒤 Mathf.FloorToInt(−localPoint.y / TotalCellSize). 한쪽만 뒤집으면 상하가 반전됩니다.
드로우 순서
아이템이 셀 위에 그려지는 것은 계층 순서(sibling index) 덕입니다. 셀은 BuildGrid에서, 아이템은 OnItemPlaced 콜백에서 생성되므로 아이템이 항상 더 나중 형제가 되고 유니티 UI는 나중 형제를 위에 그립니다. SetAsLastSibling 같은 정렬 코드가 따로 없는 이유입니다.
입력 판정
아이템이 셀을 덮으면 레이캐스트를 가로채 셀 클릭이 막힐 수 있습니다. 여기서는 문제가 되지 않았습니다 — 커서가 어느 칸인지를 레이캐스트가 아니라 좌표 계산으로 구하기 때문입니다 (ScreenPointToLocalPointInRectangle → FloorToInt). 겹치기로 한 결정이 입력 쪽에서 대가를 치르지 않은 이유입니다.
회전
회전은 루트가 아니라 아이콘 RectTransform에만 겁니다. 루트를 돌리면 anchoredPosition 기준 격자 배치까지 함께 회전해 좌표가 깨집니다. 루트 사각형은 EffectiveSize로 이미 가로세로가 뒤바뀐 상태이므로, 아이콘만 Quaternion.Euler(0, 0, −90)로 돌리고 sizeDelta의 폭·높이를 맞바꿔 채웁니다. 원본 비율은 preserveAspect가 지킵니다.

어려움

기능 03 — 배달 조건이 NPC에 묶여 확장이 막힘

문제
배달 조건이 NPC에 묶여 있어 확장이 막혔습니다. 그 NPC가 월드에 배치되어 있어야 하고, 자리를 비운 시간대에는 배달이 아예 성립하지 않았습니다. 배달지를 늘리려면 NPC를 그만큼 만들어야 했습니다. 그렇다고 팀원이 설계한 퀘스트 프레임워크를 제가 고칠 수는 없었습니다.
원인
도메인 모델이 잘못 잡혀 있었습니다. 플레이어가 실제로 하는 일은 “누구를 만나는 것”이 아니라 “어디로 가는 것”인데, 조건은 사람에 붙어 있었습니다.
해결
도메인을 장소 기준으로 다시 짜 NPC 종속 조건 4종을 제거했습니다. 프레임워크 자체는 건드리지 않고, 열어둔 확장 지점인 QuestAction에 새 액션을 추가하는 방식으로만 연결했습니다. 콘텐츠를 늘릴 때 이제 건물만 배치하면 됩니다.
