Bounce Hero : 꿈돌이

대전관광공사 마스코트를 주인공으로 한 모바일 점프 게임입니다. Google Play와 App Store 양쪽에 출시했고, 라이브 운영까지 참여했습니다.

어떤 게임인가

대전관광공사의 마스코트 꿈돌이가 발판을 밟고 위로 올라가는 캐주얼 점프 게임입니다. 위로 갈수록 발판이 줄고 멀어지고 험해지는, 끝이 없는 대신 점수로 겨루는 구조입니다. 수성부터 해왕성까지 행성 8스테이지와 히든 맵이 있고, 스테이지마다 발판 리소스가 다릅니다. 대전관광공사와 협업한 프로젝트라 오프라인 축제 현장에서도 시연했습니다.

사수와 둘이서 0부터 만든 게임입니다. 3개월 동안 저장소에 남은 커밋 302개 중 155개가 제 것이고, 발판 생성기 · 난이도 곡선 · 오브젝트 풀 · 인앱 결제 · 길드 · 랭킹은 제가 만들고 출시 뒤까지 고친 부분입니다.

기획이 정해진 상태에서 코드를 얹은 것이 아니라, 만들면서 문제를 발견하고 구조를 바꿔가며 완성했습니다. 실제 이용자에게 나간 제품을 처음부터 끝까지 겪은 경험입니다.

기능 01

끝없이 이어지는 발판 생성

카메라가 반 화면 올라갈 때마다 위쪽에 한 뭉치를 깔고, 아래로 벗어난 것은 발판 스스로 회수합니다.

구현

  • 카메라 orthographicSize와 aspect로 화면 폭을 런타임에 계산해, 기기 해상도가 달라도 같은 밀도로 깔리게 했습니다.
  • 카메라가 임계선을 넘을 때마다 발판 30개를 한 뭉치로 생성하고, 임계선을 반 화면만큼 올립니다. 생성 지점이 카메라에서 한 화면 넘게 앞서가 있으면 건너뜁니다.
  • 회수는 스포너가 아니라 발판 자신이 판단합니다. 카메라보다 아래이고 반 화면 이상 멀어진 순간 풀로 돌아갑니다. 위쪽에 있는 발판은 아무리 멀어도 건드리지 않습니다.
  • 발판을 놓은 자리에 아이템과 적을 이어서 얹되, Physics2D.OverlapCircleAll로 겹침을 먼저 확인하고 겹치면 소환을 취소해 풀로 되돌립니다.

화면

어려움

문제
확률대로 발판을 뽑다 보니 부서지는 발판이 연달아 깔리는 구간이 생겼습니다. 밟으면 사라지는 발판만 이어지면 더 올라갈 수단이 없어 플레이가 그 자리에서 끊깁니다.
원인
발판을 하나씩 독립적으로 뽑았기 때문입니다. 한 장씩 보면 모두 정상 확률이지만, 뭉치 전체로 보면 “올라갈 수 있는 길”이 보장되지 않았습니다. 확률은 개별 발판의 성질이지 경로의 성질이 아니었습니다.
해결
한 뭉치 안에 부서지는 발판은 한 번만 나오게 막고, 그 발판만은 다음 발판과의 간격을 0.3~0.4로 좁게 깔았습니다. 밟아서 사라져도 바로 위에 디딜 곳이 있게 만든 것입니다. 뽑기를 고치는 대신 뽑은 결과를 배치에서 보정했습니다.

성과

발판 7종 · 뭉치당 30개 스트리밍 해상도별 화면 폭 런타임 계산 생성 · 회수 책임 분리
기능 02

점수에 따라 올라가는 난이도 곡선

발판의 종류 · 개수 · 간격 · 적 등장을 전부 점수 하나에 물려 두었습니다.

구현

  • 현재 점수를 일정 단위로 잘라 티어로 만들고, 티어마다 발판 종류의 등장 확률표를 따로 뒀습니다. 초반에는 기본 발판 위주로, 후반에는 7종이 전부 나옵니다.
  • 같은 티어 값으로 한 뭉치의 발판 개수를 줄이고, 세로 간격을 네 배까지 벌립니다. 실제 배치는 그 값의 ±20%로 흔들어 규칙성을 지웠습니다.
  • 적은 중반 티어에 진입해야, 그것도 뭉치 몇 회에 한 마리만 나옵니다. 아이템이 놓인 발판에는 적을 얹지 않아 보상과 위협이 겹치지 않게 했습니다.
  • 난이도를 결정하는 값(티어 단위 · 간격 증가폭 · 간격 상한 · 적 등장 주기)은 전부 인스펙터에 노출해, 밸런스를 고칠 때 코드를 건드리지 않게 했습니다.

화면

어려움

문제
처음에는 발판 종류를 고정 확률로 균등하게 뽑았습니다. 기본 발판이 20%밖에 나오지 않아, 시작하자마자 부서지는 발판과 일회용 발판이 쏟아졌습니다.
원인
발판 7종을 “구현된 기능”으로 보고 똑같이 등장시킨 것이 원인입니다. 플레이어는 조작을 익히는 중인데 게임은 처음부터 모든 패를 다 꺼내고 있었습니다. 종류가 늘어난 것과 난이도가 오르는 것을 같은 일로 취급했습니다.
해결
확률을 점수 티어에 종속시켜, 발판 종류가 하나씩 순차적으로 해금되도록 바꿨습니다. 이후 “스폰 개수 증가”, “줄어드는 정도 감소” 같은 튜닝 커밋으로 곡선을 여러 번 완만하게 다시 잡았습니다.

성과

발판 7종 순차 해금 구조 난이도 파라미터 4종 인스펙터 노출 밸런스 패치를 코드 수정 없이
기능 03

타입별 오브젝트 풀과 재사용 상태 초기화

무한 스크롤 게임이라 생성·파괴가 끝없이 반복됩니다. 풀은 처음부터 설계에 넣었고, 진짜 문제는 그다음이었습니다.

구현

  • 발판 7종 · 아이템 · 적을 타입별 배열 풀로 나누고, 종류마다 초기 크기를 따로 잡았습니다. 각 종류를 미리 만들어 꺼두었다가 켜고 끄는 방식으로 바꿨습니다.
  • 풀이 비면 그만큼만 새로 만들어 풀에 넣습니다. 초기 크기를 낮게 잡아도 게임이 멈추지 않고 그만큼 늘어납니다.
  • 스테이지 테마별로 같은 프리팹에 다른 스프라이트를 물려, 발판 종류 × 테마 수만큼 프리팹을 만들지 않게 했습니다.
  • 재사용 시점을 명시적 초기화 지점으로 두고 색 · 이동 상태 · 자식 오브젝트를 전부 그 자리에서 되돌립니다.

화면

촬영 권장 — 프로파일러

Unity Profiler에서 GC Alloc이 평탄하게 유지되는 구간. 남아 있다면 “풀링이 실제로 효과가 있었다”는 말의 가장 강한 증거입니다.

어려움

문제
‘밟으면 모든 발판이 함께 움직이는’ 발판이 씬을 다시 로드하면 고장났습니다. 검은 발판은 한 번 밟혀 색이 바뀌면 다음에 꺼냈을 때도 검은 채로 나왔습니다.
원인
발판끼리는 static 이벤트로 신호를 주고받는데, 구독을 Start에서 한 번만 했습니다. 풀링은 오브젝트를 지우는 게 아니라 꺼두는 것이라 구독도 색도 그대로 남습니다. 이전 씬의 죽은 발판이 계속 이벤트를 받고 있었습니다.
해결
구독과 해제를 풀에서 꺼내고 넣는 순간(OnEnable/OnDisable)에 맞추고, 반환 시 색과 이동 상태를 되돌렸습니다. 꺼낼 때 붙어 있던 아이템·적을 먼저 떼는 처리도 같은 자리에 넣었습니다. “지워지는 것에 기대던 처리”를 전부 재사용 지점으로 옮긴 것이 이 작업의 요지입니다.

성과

사무실 테스트 기기 60 fps 유지 반복 생성·파괴를 풀 재사용으로 대체 프리팹 수를 테마 배수로 늘리지 않음
기능 04

인앱 결제 — 광고 제거 상품

두 스토어의 상품을 한 스크립트로 다루고, 구매 상태가 기기를 옮겨도 남게 만들었습니다.

구현

  • Unity IAP로 소모품 · 비소모품 · 구독 세 유형을 등록하고, 실제 판매 상품은 비소모품 ‘광고 제거’로 두었습니다.
  • 하나의 상품 정의에 스토어별 상품 ID를 매핑해, 코드 한 벌이 두 마켓을 처리하게 했습니다. 플랫폼 분기가 결제 흐름 전체로 번지지 않고 상품 등록 한 곳에만 남습니다.
  • 구매 성공 시 광고 제거 플래그를 세우고 즉시 Firebase에 저장합니다. 기기가 아니라 계정에 붙는 값이라, 같은 계정으로 다시 들어오면 구매가 남아 있습니다.
  • 애플 정책상 필수인 구매 복원 버튼을 IAppleExtensions.RestoreTransactions로 붙였습니다.

화면

어려움

문제
구매 완료를 처리하는 함수 안에서 Firebase 저장을 기다릴 수 없었습니다. 저장을 async void로 두자, 저장이 실패해도 아무도 모르게 넘어갔습니다. 돈을 낸 유저의 광고 제거가 사라질 수 있는 자리였습니다.
원인
ProcessPurchase는 스토어에 처리 결과를 즉시 돌려줘야 하는 함수라 await를 걸 수 없습니다. 그렇다고 async void로 만들면 예외가 호출자에게 전달되지 않아 실패가 조용히 삼켜집니다.
해결
저장을 Task를 반환하는 별도 래퍼로 떼어내고 그 안에서 try/catch로 실패를 잡아 로그를 남기게 했습니다. 스토어에는 결과를 바로 돌려주고, 저장은 실패해도 흔적이 남는 경로로 분리했습니다.

성과

양대 마켓 결제 · 심사 통과 계정 기준으로 구매 상태 유지 iOS · Android 결제 코드 단일화
기능 05

길드 시스템

여러 사람이 동시에 같은 길드를 건드립니다. 화면보다 동시성이 어려운 기능이었습니다.

구현

  • 길드 생성 · 검색 · 가입 신청 · 수락/거절 · 강퇴 · 해체까지 수명 주기 전체를 Firebase Realtime Database 위에 올렸습니다.
  • 가입 정책을 승인 가입 · 자유 가입 · 가입 불가 세 종류로 두고, 자유 가입은 신청과 수락을 한 흐름에서 이어 처리합니다.
  • 가입 신청과 수락은 RunTransaction으로 처리합니다. 읽고 나서 쓰는 사이에 다른 사람이 끼어들어도 길드원 목록과 신청 목록이 어긋나지 않습니다.
  • 해체는 isDisbanding 플래그를 먼저 세우고 길드원의 소속을 지운 뒤 마지막에 길드를 지웁니다. 해체 중에 들어온 가입 신청은 트랜잭션에서 중단됩니다.
  • 길드명은 Firebase 키 규칙(. # $ [ ] 불가)을 먼저 검사하고 넘깁니다.

화면

어려움

문제
길드 화면에서 길드원 전원이 같은 점수로 표시됐습니다. 그것도 하필 내 점수였습니다. 닉네임은 각자 제대로 나오는데 점수만 전부 같았습니다.
원인
목록을 그리면서 닉네임은 길드원의 ID로 조회했는데, 점수는 이미 메모리에 있던 내 데이터에서 꺼내 쓰고 있었습니다. 눈앞에 값이 있으니 가져다 쓴 것인데, 그 값은 ‘누군가의 점수’가 아니라 ‘내 점수’였습니다. 닉네임이 정상이라 화면만 봐서는 원인이 점수 쪽이라는 게 드러나지 않았습니다.
해결
점수도 길드원 ID로 각자 조회하게 바꿨습니다. 대신 정확해진 대가로 한 명당 왕복이 두 번이 됐습니다. 그래서 가입 신청 목록 쪽은 유저 데이터를 한 번에 받아 로컬에서 맞추는 방식으로 따로 처리해, 인원수와 무관하게 왕복 두 번으로 끝나게 했습니다.

성과

가입 정책 3종 · 수명 주기 전체 구현 트랜잭션으로 동시 가입 경합 차단 신청 목록 조회 왕복을 N회 → 2회
기능 06

스테이지별 랭킹

전체 하나가 아니라 스테이지마다 따로입니다. 기록도 두 종류로 나눠 저장했습니다.

구현

  • 기록을 스테이지 단위로 저장하고, 랭킹도 스테이지별로 따로 세웁니다. 행성 8스테이지가 각각 자기 순위표를 가집니다.
  • 점수 내림차순으로 정렬해 상위 100개 점수까지 표시합니다. 동점자가 묶이므로 실제로 보이는 사람은 그보다 많을 수 있습니다.
  • 동점자를 같은 등수로 묶습니다. 점수를 키로 두고 닉네임을 리스트로 매달아, 같은 점수면 같은 순위 아래에 나란히 들어갑니다.
  • 기록을 두 종류로 나눠 저장합니다. 랭킹이 쓰는 스테이지별 기록과, 길드 화면이 쓰는 전체 통합 최고 기록은 서로 다른 값입니다. 한 값으로 둘 다 감당하려 하면 “어느 스테이지의 기록인가”가 사라집니다.

화면

어려움

미작성
이 기능의 트러블슈팅은 아직 정리하지 않았습니다. 랭킹에서 막혔던 것(기록 갱신 시점, 목록 100개 그리는 비용, 해상도별 UI 배치, 닉네임 처리 등)이 있었다면 문제 / 원인 / 해결 세 칸에 맞춰 알려주시면 채웁니다.

성과

스테이지 8종 각각의 순위표 동점자 동일 등수 처리 스테이지별 · 전체 통합 기록 분리 저장
기능 07

플랫폼 SDK 연동과 라이브 운영

인증 · 광고 · 버전 관리를 붙이고, 축제 현장에서 받은 피드백을 패치로 넣었습니다.

구현

  • Firebase Auth와 Realtime Database로 계정 · 최고 기록 · 해금 상태를 처리했습니다.
  • AdMob 보상형 · 전면 광고를 붙이고, 전면 광고에 30~40초 쿨타임을 걸어 연속 노출로 플레이가 끊기지 않게 했습니다.
  • Google Play Games와 Game Center 로그인을 연동하고, 연동이 안 된 기기에서도 게임이 진행되도록 예외 처리를 따로 넣었습니다.
  • 앱 시작 시 버전을 확인해 갱신을 유도하고, 리소스 로딩 진행도를 화면에 표시했습니다.
  • 오프라인 축제 현장에서 수집한 피드백을 버그 수정과 난이도 밸런스 패치에 반영했습니다.

문제
Google Play Games · Game Center 로그인이 안 되는 기기가 있었습니다. 그런데 로그인 실패가 곧 게임 진입 실패로 이어졌습니다. 순위를 못 보는 정도가 아니라 아예 플레이를 못 했습니다.
원인
로그인 성공을 이후 흐름의 전제로 깔아 둔 것이 원인입니다. 계정 연동은 있으면 좋은 기능인데 코드에서는 필수 경로에 놓여 있었습니다.
해결
로그인 실패를 정상적인 분기 중 하나로 다시 정의하고, 실패해도 로컬 데이터로 게임이 진행되게 했습니다. 저장소에 남은 마지막 커밋이 이 예외 처리입니다.

구현

  • 디몽이 2025년 2월에 이미 Steam에 출시한 PC VR 좀비 서바이벌 게임입니다. 제가 합류한 것은 그 뒤이며, 기능 추가와 리팩터링으로 참여했습니다.
  • 게임 내 이벤트에 연동되는 Steam Achievement를 구현했습니다.
  • 무기 장착·인벤토리 레거시 코드를 파악해 무기 슬롯을 추가하며 리팩터링했습니다.

화면

어려움

문제
무기 장착과 인벤토리가 이미 서비스 중인 코드였습니다. 슬롯을 하나 늘리는 일인데 어디를 건드려야 안전한지 알 수 없었습니다.
원인
제가 쓴 코드가 아니었고, 출시된 게임이라 되돌리기 비용이 큽니다. 구조를 모른 채 고치면 기존 동작을 깨뜨립니다.
해결
먼저 레거시 코드의 흐름을 파악하는 데 시간을 썼고, 그 위에서 슬롯을 추가하며 필요한 만큼만 리팩터링했습니다. 남이 만든 구조 위에서 확장하는 방식은 이후 배달왕에서도 같은 방식으로 이어졌습니다.

범위와 한계

꿈돌이는 사수와 둘이 0부터 만들어 출시한 신규 개발입니다. 위의 기능 01–06은 제가 설계하고 구현한 뒤 출시 이후까지 고친 부분이고, 아트 리소스와 일부 UI · 광고 설정은 사수의 작업입니다. 발판 스포너의 화면 밖 이탈 방지 수정과 테마 리소스 적용처럼 사수가 제 코드 위에 얹은 수정도 있습니다. 화면 이미지는 스토어에 게시된 공식 스크린샷입니다.

ZOMVIRUS는 제가 합류하기 전인 2025년 2월에 이미 출시돼 있던 게임에 기능 추가와 리팩터링으로 참여한 것이라 출시 실적으로 세지 않습니다. 두 프로젝트 모두 제 담당은 클라이언트 구현입니다.
