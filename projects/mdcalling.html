배달왕 김족구

주문을 받아 가방에 음식을 실어 배달하는 3D 어드벤처입니다. 가방 공간을 어떻게 쓰느냐가 곧 플레이입니다.

장르
배달 어드벤처
엔진 · 언어
Unity 6 · C# · Yarn Spinner
규모 · 기간
3인 창업 팀 · 2026.01–06 (개발 01–04)
담당
인벤토리 · 대화 연동 · 배달 도메인

어떤 게임인가

NPC에게 주문을 받고, 치킨·피자 같은 음식을 가방에 넣어 목적지까지 배달합니다. 가방은 음식이 테트리스처럼 칸을 차지하는 인벤토리라, 무엇을 어떻게 넣느냐가 한 번에 받을 수 있는 주문 수를 결정합니다.

제 담당은 가방(인벤토리) 설계와 구현, 대화 시스템 연동과 선택지 UI, 그리고 배달 도메인 재설계입니다.

퀘스트 프레임워크와 마우스·게임패드 입력 체계는 팀원이 설계한 것이며, 저는 그 위에서 확장하는 쪽을 맡았습니다.

기능 01

테트리스형 인벤토리와 무게중심

음식마다 차지하는 칸 모양이 다르고 회전해서 배치합니다. 짐이 한쪽으로 쏠리면 배달통이 실제로 기웁니다.

구현

  • InventoryModel은 어느 칸에 무엇이 있는지만 알고 화면을 모릅니다. 무언가 바뀌면 알림만 쏘고, 화면 쪽이 그것을 받아 다시 그립니다.
    데이터는 InventoryItem[,]에 칸마다 그 칸을 차지한 아이템을 넣어, 3×2 아이템이면 여섯 칸에 같은 아이템이 들어갑니다.
    아이템 목록이 필요한 토크 계산용으로는 중복 없는 HashSet<InventoryItem>을 따로 둡니다.
  • 화면 쪽(InventoryGridView)은 칸 오브젝트를 InventoryCellView[,]에, 아이콘 오브젝트를 Dictionary<InventoryItem, InventoryItemView>에 담습니다.
  • 아이콘은 칸의 자식이 아니라 인벤토리의 자식입니다. 인벤토리 좌표로 위치만 받아서 칸 위에 겹쳐 그릴 수 있습니다.
  • 놓을 수 있는 자리는 인벤토리 위에 바로 보여 주고(밝은 칸), 배달통이 얼마나 한쪽으로 쏠렸는지(토크)는 아이템을 놓거나 뺄 때만 계산합니다.

화면

성과

겹침 판정에서 회전했는지 따지는 분기를 없앰 쏠림 계산은 놓거나 뺄 때만 화면이 데이터를 거꾸로 참조하지 않는 한 방향 구조 데이터 쪽은 각도를 모르고 쏠린 정도만 알림

이어서

인벤토리 직접 만져보기 실제 RecalculateTorque() 계산식을 그대로 옮긴 시뮬레이터입니다. 아이템을 놓아 보면 토크 값과 기울기가 즉시 바뀝니다. 구조 설명도 같은 페이지에 있습니다.
이 기능에서 막힌 것 아이템을 회전시키면 패드 커서가 어긋나는 현상이 발생했습니다.
여러 칸을 차지하는 아이템을 한 장의 스프라이트로 그리기
기능 02

Yarn Spinner 대화 스크립트 연동

대화가 게임 상태를 직접 묻고, 대화 도중 배달 요청 화면으로 빠졌다 돌아옵니다.

구현

  • YarnDialogueManager가 Yarn 커맨드·함수 핸들러를 등록해 .yarn 대화 스크립트를 연동합니다.
  • 게임 쪽 함수를 [YarnFunction]으로 열어 두면 대화 스크립트가 해당 함수를 이용할 수 있습니다.
    ex ) <<if has_delivery_for_pickup_location()>> - “이 장소에 받아 갈 주문이 있나”를 게임 쪽 함수로 이용함
  • 담당 파일 — YarnDialogueManager, LocalOptionPresenter, OptionItemPrefab, YarnOptionsAutoFocus.

화면

성과

대화 ↔ 상태 머신 왕복을 코루틴 하나로 대화 스크립트가 게임 상태를 직접 질의 선택지를 말하는 대상 근처에 표시
기능 03

퀘스트 구조 재설계 — 사람이 아니라 장소로

퀘스트가 늘어날 때마다 NPC를 만들어야 하는 구조를 끊었습니다.

구현

  • 이전에는 대화를 NPC에 의존했습니다. 대화 시작 노드가 NpcController의 데이터에 박혀 있어서, 배달지를 하나 늘리려면 그 대화를 들고 있을 NPC 게임오브젝트를 월드에 새로 배치해야 했습니다.
  • Location을 ScriptableObject로 만들고, 대화를 누가 들고 있느냐를 NPC에서 장소(PlaceInteractable)로 옮겼습니다. 말을 거는 대상이 건물 자체가 되고, 등장 인물은 장소 대화 UI의 캐릭터 스프라이트로 그려집니다. 덕분에 한 장소에 여러 인물을 세울 수 있고, NPC 오브젝트를 늘리지 않아도 됩니다.
  • QuestAction 확장점에 액션을 추가해 그 장소의 Yarn 시작 노드를 갈아끼웁니다. 그래서 진행도에 따라 대화가 바뀔 수 있습니다.
    원래 대화로 되돌리는 defaultYarnStartNode 경로도 함께 뒀습니다.

화면

성과

팀 프레임워크 수정 0 대화 시작 노드의 소유자를 NPC → 장소로 이전 한 장소에 여러 인물 — NPC 오브젝트 증식 차단 퀘스트 진행도에 따라 장소의 대화 노드 교체

이어서

퀘스트 프레임워크 구조 분석 확장하기 전에 팀 프레임워크를 어디까지 파악했는지 — 계층·상태·보고 흐름 다이어그램으로 정리했습니다.
이 기능에서 막힌 것 배달 조건이 NPC에 묶여 확장이 막힘
기능 04

게임패드 내비게이션과 하이브리드 입력

유니티 자동 내비게이션은 아이템 크기를 모릅니다. 커서 이동을 직접 짜고, 마우스와의 차이는 한 곳에서 흡수했습니다.

구현

  • 인벤토리는 드래그 앤 드롭이라 “지금 어느 칸을 가리키는가”가 있어야 성립합니다. 그런데 그 값을 얻는 방법이 장치마다 다릅니다 — 마우스는 화면 좌표를 그대로 주지만, 게임패드에는 좌표라는 개념이 없고 EventSystem이 선택한 UI 오브젝트만 있습니다.
  • 그래서 게임패드 쪽은 선택된 칸의 화면 중심을 커서 좌표로 만들어 넘깁니다. 입력을 IInventoryInputProvider 하나로 추상화해, 그 아래 코드는 마우스인지 패드인지 알 필요 없이 좌표값만 받아서 씁니다.
  • 이동 계산만 직접 짰습니다. 유니티 Selectable의 Navigation(Automatic)은 화면상 위치만 보고 다음 대상을 고릅니다. 피자가 3×2를 차지하면 오른쪽 한 번에 3칸을 건너뛰어야 하는데, Navigation은 그게 안 되서 이동을 구현했습니다.
  • 그리드 왼쪽 끝에서 왼쪽을 더 밀면 바깥 영역으로 넘어가고, 바깥에서 그리드 쪽으로 밀면 가장자리 칸으로 들어옵니다. 바깥 영역도 같은 EventSystem 체계 안에 있어 이동이 끊기지 않습니다.

화면

판단

왜 인터페이스를 붙이지 않았나

만든 것
입력 인터페이스와 장치별 구현체 둘을 완성했습니다. 커서 좌표 하나와 이벤트 넷(집기 누름·뗌, 취소, 배출)으로 컨트롤러가 알아야 할 것을 줄이는 설계였습니다.
다시 본 것
팀의 상태 머신이 이미 버튼별 진입점을 열어두고 있었습니다. 인터페이스가 흡수하려던 차이는 그 진입점 안에서 if 하나로 갈리는 것이었고, 컨트롤러가 실제로 필요로 한 값은 좌표 하나뿐이었습니다.
기준
추상화는 대상이 앞으로 늘어날 때 가치가 있습니다. 입력 장치는 마우스와 게임패드 둘에서 멈출 예정이었고, 그 둘을 이미 구분할 수 있으니 계층을 하나 더 두면 읽을 코드만 늘어난다고 봤습니다.
한 것
환산 로직을 InventoryState로 옮기고 인터페이스는 붙이지 않았습니다. 목표는 그대로 달성했고 불필요한 클래스를 생성하지 않았습니다.

성과

아이템 크기를 아는 커서 이동 — 다중 칸 아이템에서 헛돌지 않음 컨트롤러가 마우스·게임패드를 구분하지 않음 장치 전환이 매 프레임 자동 — 조작이 끊기지 않음 같은 목표를 클래스를 추가하지 않고 구현

이어서

입력 처리 — 설계와 판단 근거 처음 설계한 인터페이스, 옮긴 뒤의 실제 구조, 그리고 그렇게 판단한 근거를 정리했습니다. 팀 배관과 본인 작업의 경계도 3층 표로 나눠 두었습니다.
이 기능에서 막힌 것 아이템을 회전시키면 패드 커서가 어긋나는 현상이 발생했습니다.

어려움

기능 01 · 04 - 아이템을 회전시키면 패드 커서가 어긋나는 현상이 발생했습니다.

문제
배치·충돌·렌더링은 회전을 반영하는데, 게임패드 커서가 회전한 아이템 위에서 엉뚱한 칸으로 점프했습니다. 예를 들어 5×5 인벤토리에서 4×2 피자를 회전해 세로로(실제 2×4) 놓고 오른쪽을 누르면 x=1 → x=4로 뛰어, 피자 바로 옆 빈 칸(x=3)에 갈 수 없었습니다. 무게중심 계산도 같은 증상으로 한 칸 어긋나 있었습니다.
원인
회전한 크기를 EffectiveSize라는 파생 프로퍼티(값을 따로 저장하지 않고, 물어볼 때마다 원본 크기와 회전 여부로 계산해 돌려주는 속성)로 만들었습니다. 그러면 쓰는 쪽은 회전했는지 따질 필요 없이 크기만 물어보면 됩니다. 그런데 나중에 추가한 커서 이동과 무게중심 계산이 EffectiveSize를 안 쓰고 원본 크기를 그대로 가져다 썼습니다. 테스트에 쓴 아이템 하나가 정사각형이라 회전해도 크기가 안 바뀌었고, 그래서 오래 드러나지 않았습니다.
배운 것
파생 프로퍼티는 나중에 코드를 쓰는 사람이 "그 값을 써야 한다"는 걸 알고 있어야 성립합니다. 원본 크기를 꺼내 쓸 수 있게 열어두면 그 전제는 언젠가 깨집니다. 지금이라면 원본 크기를 아예 못 꺼내게 막아, 인벤토리를 다루는 코드가 EffectiveSize만 쥐게 하겠습니다. 개발 종료 후 발견해 수정하지 않고 기록만 남겼습니다.

어려움

기능 01 — 여러 칸을 차지하는 아이템을 한 장의 스프라이트로 그리기

문제
가방은 고정 크기 칸이 늘어선 인벤토리인데 아이템은 한 칸이 아니라 EffectiveSize만큼 여러 칸을 차지합니다. 칸마다 스프라이트를 타일링하면 치킨 스프라이트가 2*2 칸에 하나씩 들어갑니다. 아이템 하나는 몇 칸을 덮든 스프라이트 한 장이어야 했습니다.
원인
인벤토리 UI를 짜면 자연히 아이템 RectTransform을 칸의 자식으로 넣게 됩니다. 그런데 자식이 되는 순간 아이템은 부모 칸의 사각형에 묶여 한 칸 크기를 넘어설 수 없습니다. 부모를 넘어 여러 칸을 덮을 방법이 없었습니다.
해결
아이템 뷰를 칸의 자식이 아니라 인벤토리 루트의 형제로 생성해 (Instantiate(itemPrefab, _rectTransform)) 칸 층 위에 겹쳤습니다.

어려움

기능 03 — 배달 조건이 NPC에 묶여 확장이 막힘

문제
배달 조건이 NPC에 묶여 있어 확장이 막혔습니다. 그 NPC가 월드에 배치되어 있어야 하고, NPC 두 명을 동시에 출연시키기 힘들었습니다. 배달지를 늘리려면 NPC를 그만큼 만들어야 했습니다. 그렇다고 팀원이 설계한 퀘스트 프레임워크를 제가 고칠 수는 없었습니다.
해결
장소 기준으로 다시 짜 NPC 종속 조건을 제거했습니다. 프레임워크 자체는 건드리지 않고, 열어둔 확장 지점인 QuestAction에 새 액션을 추가하는 방식으로만 연결했습니다. 콘텐츠를 늘릴 때 이제 건물만 배치하면 됩니다.

3인 창업 팀 프로젝트이고, 이 페이지는 인벤토리 · 대화 연동 · 배달 도메인 · 입력 처리까지 제가 맡은 구간입니다. 퀘스트 프레임워크와 입력 바인딩 체계는 팀원이 설계한 것이며, 저는 그 프레임워크를 고치지 않고 열어 둔 확장 지점 위에서만 붙였습니다. 개발은 2026.01–04이고 이후 6월까지는 발표 준비 기간입니다.
