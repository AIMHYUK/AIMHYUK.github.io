MiniOscReceiver

Stage On에서 골랐던 OSC 수신 구조를 플러그인 없이 직접 다시 만들어 측정한 실험입니다. 나중에는 그때 포기했던 재전송 구조까지 다시 세워 인터넷 너머로 보내봤습니다.

왜 만들었나

Stage On에서 모션 데이터를 RPC 대신 UDP/OSC로 받도록 바꾼 판단이 있었습니다. 그런데 그때 소켓·수신 스레드·바이트 파싱은 플러그인이 처리했고, 제가 실제로 확인한 것은 “끊겨 보이던 게 나아졌다”는 증상뿐이었습니다.

그래서 플러그인이 감추고 있던 그 계층을 직접 만들고, 같은 데이터를 RPC로도 보내는 비교군을 함께 세워 나란히 재봤습니다.

기능 01

UDP 소켓과 전용 수신 스레드

게임 프레임을 기다리지 않고, 전용 스레드가 1ms마다 소켓을 확인합니다.

구현

  • FUdpSocketBuilder로 소켓을 열고 수신 버퍼를 1MB로 잡았습니다.
  • FUdpSocketReceiver가 만든 전용 스레드에서 1ms마다 폴링합니다.
  • 종료는 스레드를 먼저 멈추고 그다음 소켓을 닫습니다. 소켓은 delete가 아니라 서브시스템에 DestroySocket으로 반납합니다.

화면

성과

송신 Hz를 그대로 따라가는 수신 에디터 실행(PIE)을 껐다 켜도 포트가 잡힌 채 남지 않음
이 기능에서 막힌 것 UDP 소켓과 전용 수신 스레드
기능 02

RPC와 비교 측정

같은 데이터를 OSC와 RPC 양쪽으로 보내, 부하를 올렸을 때 어떤 차이가 발생하는지 측정했습니다.

구현

  • 같은 궤도 데이터를 RPC로도 보내는 비교군(RpcMotionActor)을 만들고, 양쪽에 같은 계측 컴포넌트를 붙였습니다.
  • 조건은 똑같이 두고 전송 방식(OSC vs RPC)만 바꿨습니다.
    · SetReplicateMovement(false)로 엔진이 알아서 해 주는 위치 동기화를 껐습니다 — 안 끄면 RPC가 도착하든 말든 큐브가 움직여 측정이 무의미해집니다.
    · HasAuthority()(서버 쪽)일 때는 재지 않았습니다 — 서버는 호출한 함수가 그 자리에서 실행되니 전달률이라는 게 없습니다.
  • 뼈(본) 개수를 1개 → 100~200개로 올렸습니다. Stage On 실데이터는 본 56 + 표정 52 = 한 포즈 108값이므로, 실제의 1~2배 부하입니다.

화면

촬영 조건두 경로를 동시에 돌리면 서로 부하를 주므로 각각 단독으로 재고 송신 조건만 맞췄습니다. OSC 촬영 시 RPC 액터를, RPC 촬영 시 OSC 송신기를 껐습니다.

방식초당 요청클라 수신전달률유실결과
RPC · Reliable24,000—측정 불가—연결 종료
RPC · Unreliable24,0001120.47%310,628연결 유지, 사실상 마비
OSC · UDP24,12024,120100%0전부 수신

초당 요청 수가 다른 이유RPC는 본만 보내 200 × 120Hz = 24,000이고, OSC 송신기는 프레임마다 페이셜 패킷 /face/blend 하나를 더 보내 (200+1) × 120Hz = 24,120입니다. OSC 쪽이 120개 더 많은 부하를 받고도 유실이 0이었습니다.

성과

OSC 전달률 100% · 유실 0 구조 선택의 근거를 직접 만들어 측정 세 방식의 실패 양상이 다르다는 결론

이어서

이 판단이 나온 곳 · Stage On 여기서 측정한 구조 선택을 2년 전에 실제로 내렸던 프로젝트입니다.
기능 03

OSC 바이트 파싱

도착한 바이트 덩어리에서 주소와 숫자를 파싱합니다.

구현

  • 4바이트 정렬 — (n + 3) & ~3. /cube/pos는 9글자지만 널 포함 12바이트를 소비합니다.(4의 배수를 맞춰야 하기 때문)
  • 빅엔디안 조립 — OSC는 네트워크 바이트 오더(큰 자리를 앞에 두는 순서)입니다. 가장 앞 바이트를 최상위로 두고 조립합니다.
  • float는 값을 바꾸지 않고 비트만 다시 읽습니다 — FMemory::Memcpy로 32비트를 그대로 옮깁니다.
  • 매 읽기마다 경계를 검사하고, 모르는 타입 태그를 만나면 즉시 실패시킵니다.

기능 04

스레드 경계 — SPSC 락프리 큐

넣는 쪽과 받는 쪽을 구분했습니다. SPSC는 넣는 쪽 하나 · 꺼내는 쪽 하나, 락프리는 서로 기다리지 않는다는 뜻입니다.

구현

  • 수신 스레드는 파싱해서 큐에 넣는 일까지만 합니다. TQueue<FOscMessage, EQueueMode::Spsc>로 게임 스레드에 넘깁니다.
  • 계측 카운터조차 FPlatformAtomics::InterlockedIncrement로 atomic한 동작으로 증가시킵니다. ++는 읽고·더하고·쓰는 세 동작이라 중간에 끼어들면 값이 어긋납니다.
  • 게임 스레드는 Tick에서 큐를 비우고 주소 패턴으로 갈라 위치는 Transform에, 표정(페이셜)은 로그로 보냅니다.

성과

수신 스레드가 게임 스레드를 기다리지 않음 두 스레드가 같은 값을 동시에 건드려 생기던 크래시 제거
이 기능에서 막힌 것 스레드 경계 — SPSC 락프리 큐
기능 05

본을 묶어서 압축

Stage On 발표 원고에 적었던 “다시 한다면 프레임마다 본을 묶어서 보낼 것 같다”를 실제로 해보고 바이트를 쟀습니다.

구현

  • 실패 커밋의 RPC 구조를 그대로 떼어와, 본 하나당 RPC가 아니라 프레임당 1회 · 본 전체를 한 덩어리로 조건을 바꿨습니다.
  • 페이로드를 3단계로 줄였습니다.
    · 본 이름 제거 — 양쪽이 같은 순서를 알면 인덱스로 충분합니다.
    · 회전 쿼터니언 4성분을 각각 float → int16 (본당 16B → 8B).
    · 위치는 루트 하나만 — 계층 구조라 나머지 본은 회전만으로 자세가 복원됩니다. 스케일은 어차피 1이라 보내지 않습니다.
    · 표정 값은 float → uint8 — ARKit이 0~1로 주므로 1/255 단위면 충분합니다.
  • RPC를 아예 빼고 UDP 멀티캐스트로도 다시 만들었습니다. 21바이트 헤더를 직접 정의하고, 언리얼 수신기 · 송신기 · 중계기를 모두 만들어 파이썬 대조군과 같은 와이어 포맷으로 나란히 쟀습니다.

화면

측정 조건본 56 + 표정 52. 본 개수와 표정 개수를 따로 0으로 두고 차이를 재서 뽑은 실측값이며 산술 추정이 아닙니다.

성과

호출당 6,868B → 526B (7.7%) 유실 76.6% → 0.14% 멀티캐스트 기준 200본 12,057B → 1,685B (7.2배)
기능 06

실제 회선에서 측정 — 인터넷 너머까지

루프백에서는 셋 다 유실 0이었습니다. 압축의 값어치는 실제 회선에서만 드러났습니다.

구현

  • 언리얼이 깔려 있지 않은 노트북에서도 돌리려고 패키징 빌드를 만들고, 그룹 주소 · 랜카드 · 포트를 커맨드라인으로 덮어쓸 수 있게 했습니다. 수신 액터도 콘솔 없이 자동으로 뜨도록 서브시스템을 붙였습니다.
  • 유선(데스크탑) → Wi-Fi(노트북) 로 압축 3단계를 각각 3,000프레임씩 보냈습니다.
  • 언리얼 수신기를 무선 쪽에 놓고 파이썬 대조군을 같은 랜카드에 동시에 붙였습니다. 혼자 재면 숫자가 나빠도 회선 탓인지 언리얼 탓인지 가를 수 없기 때문입니다.
  • 마지막으로 호스트가 방을 열고, 휴대폰 핫스팟에 물린 노트북이 공인 IP로 접속하게 했습니다. 같은 공유기에 붙어 있으면 공인 IP로 접속해도 인터넷을 타지 않습니다(헤어핀 NAT).

성과

실제 무선 구간에서 압축 전 약 70% → 양자화 후 0% 인터넷 너머 본 200개 · 60Hz 유실 0 언리얼 수신기와 파이썬 대조군 유실률 일치

어려움

기능 01 — UDP 소켓과 전용 수신 스레드

문제
게임 스레드에서 소켓을 읽으면 프레임당 한 번밖에 확인하지 못합니다. 그 사이 도착한 패킷이 커널 버퍼에 쌓이다 넘칩니다.
원인
UDP는 재전송이 없습니다. 버퍼가 차면 커널이 버리고 애플리케이션은 그 사실조차 모릅니다.
해결
수신을 전용 스레드로 분리해 1ms마다 확인하고, 커널 버퍼도 크게 잡았습니다. 1ms면 60~120Hz 스트림을 놓치지 않으면서 CPU 부하도 크지 않습니다.

어려움

기능 03 — OSC 바이트 직접 파싱

문제
조립한 0x3FC00000을 (float)로 캐스팅했더니 약 10억이 나왔습니다. 기대한 값은 1.5였습니다.
원인
캐스팅은 값을 변환합니다. 제가 원한 것은 변환이 아니라 같은 32비트를 IEEE754 규칙으로 다시 읽는 것이었습니다. 
// 같은 32비트, 처리 방식만 다르게

① (float)Bits — 값 변환
   전  0011 1111 1100 0000 0000 0000 0000 0000
   후  0100 1110 0111 1111 0000 0000 0000 0000  → 1069547520.0
       비트를 새로 만든다. 양은 보존, 비트는 버림.

② Memcpy(&f, &Bits, 4) — 비트 재해석
   전  0011 1111 1100 0000 0000 0000 0000 0000
   후  0011 1111 1100 0000 0000 0000 0000 0000  → 1.5
       한 비트도 안 바뀐다. 읽는 규칙만 IEEE754로.
해결
FMemory::Memcpy로 비트를 그대로 복사했습니다. reinterpret_cast도 가능하지만 strict aliasing 위반 소지가 있어(컴파일러에 따라 깨질 수 있음) Memcpy를 택했습니다.

어려움

기능 04 — 스레드 경계 — SPSC 락프리 큐

문제
수신 콜백에서 액터를 직접 움직이면 값이 절반만 갱신되거나 크래시가 났습니다.
원인
언리얼의 UObject는 스레드 세이프하지 않습니다. 게임 스레드가 큐브의 위치를 읽어서 그리는 한복판에 수신 스레드가 값을 덮어써서 그 결과로
- 값이 절반만 갱신됨 (x는 새 값, y는 옛 값)
- GC가 그 순간 그 오브젝트를 정리 중이었다면 → 이미 해제된 메모리를 건드림 → 크래시
해결
컨베이어 벨트처럼, 큐 하나를 두고 올리는 쪽(수신 스레드)과 내리는 쪽(게임 스레드)을 구분했습니다. 락은 쓰지 않았습니다. 수신 스레드가 락이 풀리기를 기다리며 멈추면 그동안 소켓을 못 읽어 커널 버퍼가 차고, 결국 데이터 유실로 이어지기 때문입니다. 생산자·소비자가 각각 하나로 확정돼 있어 SPSC로 충분했습니다.

어려움

기능 06 — 공유기가 멀티캐스트를 무선으로 넘기지 않음

문제
Stage On에서 쓰던 그룹 주소 239.1.1.1로 보냈더니 노트북에 한 개도 오지 않았습니다. 같은 노트북에 유니캐스트로 직접 보내면 300개 중 300개가 정상 수신됐으므로 방화벽·서브넷 문제가 아니었습니다.
원인
공유기가 IGMP 스누핑으로 유선 구간과 무선 구간 사이의 239.x 트래픽을 걸러냅니다. 239.0.0.0/8은 RFC 2365가 조직 내부용으로 규정한 대역이라 밖으로 나가지 않는 것이 규격상 정상입니다.
해결
링크로컬 제어 대역인 224.0.0.1로 옮겨 측정했습니다. 다만 이것 자체가 결과이기도 합니다 — 가정용 공유기에서는 “호스트가 받아서 관객 PC로 멀티캐스트 재전송”이라는 설계가 기본 설정으로는 성립하지 않습니다. 당시 재전송을 포기하고 각 PC 직접 수신으로 되돌린 판단이, 일정 문제를 떠나 구조적으로도 맞았다는 근거가 됩니다.

어려움

기능 06 — 유실의 원인이 회선이 아니었음

문제
인터넷 너머로 접속시키자 약 25%가 유실됐습니다. 그런데 보내는 양은 초당 100KB 남짓이라 핫스팟이 그걸 못 버틸 수준이 아니었습니다.
원인
회선을 완전히 빼고 같은 기계 루프백에서 재봤더니 거기서도 유실이 났습니다. 패킷이 물리적으로 사라질 곳이 없으니 엔진 쪽이었습니다. 커넥션 대역폭 상한을 바꿔가며 재니 유실이 그대로 따라 움직였습니다. 
// 상한만 바꾸고 나머지는 동일 — 200본 양자화 60Hz
  50,000 B/s   유실 55.7%
 100,000 B/s   유실  8.8%   ← 언리얼 기본값
 105,000 B/s   유실  2.4%

엔진 기본 상한이 100,000 B/s인데 보내려던 데이터가 100.7 KB/s였습니다. 딱 그 선을 넘고 있었습니다. 헤더 오버헤드로 상한의 약 92%만 실제 데이터에 쓸 수 있어, 문턱을 109 KB/s로 예측하고 105k · 110k로 확인했습니다.
해결
서버 상한과 클라이언트 요청 속도를 둘 다 올렸습니다(한쪽만 올리면 8.8% → 6%로 그칩니다). 같은 회선에서 25% → 0%가 됐습니다.
다만 상한을 올리는 것이 근본 해법은 아닙니다. 대역폭이 생기는 게 아니라 병목이 회선으로 옮겨갈 뿐이고, 관객 수만큼 부하가 곱해집니다. 압축하지 않은 원본은 본 56개만으로도 초당 402KB라 기본 상한의 4배여서, 설정으로는 넘길 수 없습니다. 압축이 먼저고 설정은 그 다음입니다.

여기서 한 번 틀렸습니다 계측 조건에 따라 유실이 8.8%와 45%로 갈리는 것을 보고 “두 프로세스가 CPU를 다툰다”고 단정했습니다. 나중에 CPU 사용량을 재보니 32코어 중 10%만 쓰고 있었고, 프레임 제한 없이 상한만 올려도 유실이 0이 됐습니다. 원인은 대역폭 상한 하나였고 프레임레이트는 조절 변수였습니다. 재지 않고 원인을 지목하면 안 된다는 것을 여기서 배웠습니다.

범위와 한계

기능 01~04는 PIE에서 쟀습니다. 리슨 서버가 클라이언트와 같은 프로세스라 통신이 물리 네트워크를 타지 않습니다. 그래서 거기서 관찰된 실패는 전부 엔진 내부 한계(Reliable 버퍼 오버플로, 게임 스레드 정체)입니다. 그 한계를 메우려고 기능 05~06을 붙였습니다 — 다른 PC로, 무선으로, 마지막엔 인터넷 너머로 실제 회선을 태웠습니다.

그래도 남는 것이 있습니다. 관객은 1명까지만 쟀습니다. 멀티캐스트와 달리 RPC 경로는 송신 부하가 관객 수에 비례하는데, 관객이 늘 때 호스트 업로드가 어디서 무너지는지는 보지 않았습니다. 두 기계 사이의 지연도 못 쟀습니다 — 시계 원점이 달라 값이 무의미합니다. 무선 구간 측정은 공유기 한 대 · Wi-Fi 한 종류의 결과이고, 회차마다 흔들려 같은 조건을 시간대를 달리해 재면 값이 흩어집니다. 그래서 결론은 같은 세션에서 붙여 잰 A/B로만 냈습니다.

NetServerMaxTickRate 조작이 PIE에서 적용되지 않아 틱레이트의 영향은 검증하지 못했습니다. 조각 개수는 Stage On 실데이터(본 56 + 표정 52 = 108값)의 1~2배로 맞췄지만, 본 하나가 위치(float 3개)뿐이라 회전까지 보내는 실제 모션캡처보다 본당 데이터는 가볍습니다. 개수는 맞춰도 바이트는 덜 실은 셈이라, 이 수치를 실제 환경의 값으로 읽어서는 안 됩니다.
