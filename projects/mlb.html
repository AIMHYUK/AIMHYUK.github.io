어떤 게임인가

캐릭터는 스스로 전진하고, 마주치면 무기 가중치로 밀고 밀리며 자동으로 공격을 주고받습니다. 플레이어가 개입하는 것은 직업 고유 스킬 · 대시 · 방향 전환 세 가지뿐입니다. 라운드마다 유물을 하나씩 골라 15라운드를 쌓습니다.

데이터 위주의 설계로 전투의 모든 수치가 데이터로 빠져 있고, 판정은 프레임 단위로 정의되며, 모든 수치는 서버가 계산합니다.

진행 상황(2026-08 기준) — 서버 권위 구조 · 강제 이동 궤적 · 판정 · 상태/데이터 레이어 · 유물 파이프라인은 완료했고, 스킬과 무기 강화 등 콘텐츠 볼륨과 밸런스가 9월 중순까지 남아 있습니다. 넥슨 글로벌 개발 콘테스트 출품 예정(10/7 마감).

촬영 필요 — 대표 화면

자동 전투가 벌어지는 아레나 화면. 여러 캐릭터가 붙어 있고 체력·유물 UI가 보이면 “무슨 게임인지”가 한 장으로 전달됩니다. MSW Maker의 Play 화면을 캡처하면 됩니다.

기능 01

이동 권위를 서버 하나로 — 네 번 갈아엎고 도착한 곳

각자의 클라이언트가 굴리던 이동을 서버가 정하는 것(권위)으로 옮기는 동안, 게임이 한 번도 멈추지 않게 했습니다.

구현

  • 붙일 자리를 네 번 바꿨습니다. 런타임에 컴포넌트를 붙이는 방식이 이 플랫폼에서 막혀 있었고, 전역 로직이 로컬 플레이어를 직접 굴리는 방식은 인원이 늘면 무너졌습니다. 커스텀 플레이어 모델에 구워 넣는 우회를 거쳐, 결국 기본 플레이어 모델에 직접 붙이는 것으로 정착했습니다. 마지막 단계는 새로 만든 게 아니라 만들었던 우회로 셋을 지운 것입니다.
  • 셋으로 갈랐습니다 — 이동 공식(BRMoveSim)은 바깥의 무엇도 참조하지 않고 같은 입력이면 언제나 같은 결과를 내는 순수 함수(결정론)로, 상태(BRStatus)는 붙였다 떼는 이름표(태그) 묶음으로, 구동(BRPlayerDriver)은 플레이어를 매 프레임 굴리는 단 하나의 진입점 (OnUpdate)으로.
  • 드라이버를 하나로 모은 이유가 핵심입니다 — 이 플랫폼은 같은 엔티티에 붙은 컴포넌트들의 OnUpdate 순서를 보장하지 않습니다. 각자 자기 OnUpdate를 가지면 “상태 → 이동 → 전투” 순서가 프레임마다 뒤바뀌고, 결정론이 깨지면 서버와 클라가 다른 결과를 냅니다. 그래서 틱 순서를 코드로 명시했습니다.
  • 이관은 4단계로 쪼갰습니다. 자동공격 → 대시 → (봇 통합은 도중에 불필요해져 생략) → 드라이버 스택 삭제. 각 단계마다 양쪽이 동시에 존재해도 동작하는 상태를 유지했고, 드라이버가 서버 컨트롤러의 존재를 감지하면 운전을 양보하게 만들어 이관 중 더블 드라이브(캐릭터가 뒤를 보거나 공격 모션이 씹히는 증상)를 막았습니다.
  • 이관하면서 2인 고정을 인원 제한 없는 명단(레지스트리)으로 바꿨습니다. 각 캐릭터의 좌표와 방향을 userId를 열쇠로 삼는 공유 표에 두고, 각 파이터가 자기 최근접 상대만 보고 판단하게 해서 2명이든 M명이든 같은 규칙으로 돕니다.

화면

어려움

문제
서버 권위로 옮기던 중 같은 캐릭터의 체력이 두 벌로 갈라졌습니다. 서버에서 피해를 넣고 양쪽에서 같은 엔티티를 읽으니 786 / 1000으로 어긋났습니다.
원인
체력이 평범한 프로퍼티였고 피해 처리 메서드에 실행 공간 지정이 없었습니다. 이 언어에서 실행 공간이 없는 메서드는 호출한 쪽의 공간에서 돕니다. 봇의 틱은 서버에서, 플레이어의 틱은 클라이언트에서 돌고 있었으니 각자 자기 사본만 깎은 것입니다. 무서운 건 아무도 에러를 내지 않는다는 점입니다 — 플레이어는 자기가 맞는 걸 못 보고, 서버는 상대가 죽는 걸 못 봅니다. 여기에 사망·라운드 종료를 붙였다면 양쪽이 다른 시점에 발동합니다.
해결
값마다 주인을 먼저 정하는 규칙을 세웠습니다 — 상태 값은 서버가 바꾸면 전원에게 퍼지는 값(동기화 프로퍼티)으로 두고 서버가 유일한 소유자, 상태를 바꾸는 메서드는 클라가 불러도 서버에서 실행, 읽기 전용 판정만 무주석으로 둬서 클라가 동기화된 값을 읽게 했습니다. 같은 시기에 밀림 힘겨루기가 한쪽으로 편향된 형제 버그도 나왔는데, 상대의 방향 값이 동기화되지 않아 상대 클라에만 존재했던 것이라 같은 규칙으로 정리됐습니다.

성과

이동 공식은 구동 주체가 클라 → 서버로 바뀌는 동안 한 줄도 안 바뀜 2인 고정 → 인원 제한 없는 명단(레지스트리) 이관 4단계 내내 더블 드라이브 0건
기능 02

넉백을 서버 권위로 — 물리를 버리고 결정론적 궤적으로

“어떻게 클라를 못 믿게 만들까”를 “왜 클라에게 물어보나”로 바꾸자 방어 코드가 통째로 사라졌습니다.

구현

  • 먼저 두 번 실패했습니다. ① 서버에서 리지드바디에 힘을 주는 방식 — 로컬에서는 포물선을 그리며 잘 날아갔는데 원격 플레이어는 높이 0.73에서 평평하게, 수평으로 0.11 유닛만 가고 멈췄습니다. 플랫폼 문서에 플레이어 리지드바디는 클라이언트 → 서버 방향으로 동기화된다고 한 줄로 적혀 있었습니다. ② 클라이언트가 물리를 굴리고 착지를 서버에 보고하는 방식 — 느낌은 이쪽이 제일 좋았지만 착지 시각을 클라이언트가 정합니다.
  • 구멍의 크기를 재봤습니다. 체공 중 무적인 스킬에 같은 구조를 쓰고 있었는데, 실제 체공 1.0초에 서버 측 상한이 1.5초였습니다. 보고를 보내지 않는 클라이언트는 땅에 선 채로 0.5초 추가 무적을 얻습니다. 최소 잠금 시간으로 막아봤지만 그건 증상만 가리는 것이라, 상한과 하한 사이는 여전히 클라가 정합니다.
  • 그래서 서버가 계산으로 알 수 있는 궤적으로 바꿨습니다. 격투게임이 실제로 쓰는 방식입니다 — 넉백은 물리 시뮬레이션이 아니라 저작된 커브라야 콤보가 프레임 단위로 재현됩니다. 궤적을 { 시작 위치, 이동량, 지속시간 }으로 정의하고 서버가 매 틱 진행률로 수평 위치를 계산합니다.
  • 수평은 서버가 소유하고, 수직은 순수 연출입니다. 판정(접촉 · 밀림 · 사거리 · 겹침 분리)이 전부 수평만 보므로 서버가 수평만 정확히 굴리면 판정은 완결됩니다. 높이는 클라이언트가 같은 진행률 · 같은 공식으로 그립니다. 서버는 높이를 모르고, 알 필요도 없습니다.
  • 높이 곡선은 4h·t(1-t)를 썼습니다. 진행률 0과 1에서 정확히 0이라 땅에 박히거나 공중에서 끝나는 상태가 원천적으로 없습니다.
  • 넉백 · 대시 · 점프를 같은 자료구조 하나로 합쳤습니다. 셋 다 “플레이어 의지와 무관하게 정해진 궤적으로 옮겨지는 이동”이라 행동 불능 게이트가 “진행 중인 궤적이 있는가” 한 줄이 됩니다. 대시는 부수적으로 이득을 봤습니다 — 예전엔 목적지를 즉시 대입해서 서버는 이미 도착했다고 보고 클라는 아직 가는 중이라 판정이 화면과 어긋났는데, 0.12초짜리 궤적으로 바꾸니 양쪽이 일치합니다.

화면

촬영 권장 — 넉백 궤적

맞은 캐릭터가 포물선을 그리며 날아가는 순간. 상 등급이 가장 잘 보입니다.

어려움

문제
서버에서 힘을 주는 첫 구현이 제 테스트에서는 완벽하게 동작했습니다. 포물선도, 착지도 자연스러웠습니다. 그런데 2인 테스트에서 “되긴 하는데 한 번 쓰면 안 날아가고 여러 번 써야 날아간다”는 보고가 왔습니다.
원인
제 테스트가 처음부터 유효하지 않았습니다. 이 플랫폼의 플레이 테스트는 서버와 클라이언트가 한 프로세스에 뜨지만 논리적으로는 별개입니다. 제가 힘을 준 대상은 서버가 소유권을 가진 것처럼 보이는 로컬 플레이어였고, 실제 멀티 환경의 원격 플레이어와는 조건이 달랐습니다. 개발 환경이 권위 문제를 가리고 있었습니다.
해결
원격 대상으로 다시 측정해 수치를 확보하고 커밋을 통째로 되돌렸습니다. 이후 권위가 걸린 기능은 반드시 원격 대상으로 측정한다를 원칙으로 세웠습니다. 커밋을 잘게 쪼개 둔 덕에 되돌리기가 한 번으로 끝났습니다 — 실패를 인정하는 비용을 낮춰두는 것도 설계의 일부라고 봅니다.

성과

위치 · 시간 · 행동 불능 해제 권위 100% 서버 — 클라가 보내는 것이 없으므로 조작할 것도 없음 조종 해제/복구 · 착지 감지 · 보고 RPC · 최소 잠금 방어 코드 전부 삭제 강제 이동 3종을 자료구조 하나로 통합

포기한 것도 적어둡니다 — 진짜 물리의 자연스러움(착지 반동 · 경사면 · 다른 물체와의 충돌 반응)을 잃었습니다. 평지 아레나에서 정해진 거리만 날아가면 되는 이 게임에서는 손해가 없지만 지형이 복잡해지면 재검토해야 합니다. 수평 감속도 물리적으로는 정확하지 않습니다 — 타격감을 위해 의도적으로 어긴 것이라 코드에 그렇게 명시하고 되돌리는 방법을 주석에 남겼습니다.

기능 03

상태와 수치를 코드 밖으로 — 태그 · 데이터 3층 · 직업 8종

스킬을 붙이기 전에 인프라를 먼저 깔았더니, 스킬 8종이 붙을 때 호출부를 한 줄도 안 고쳤습니다.

구현

  • 상태를 boolean 필드에서 태그 집합으로 바꿨습니다. 스턴 · 침묵 · 이동정지 · 넉백 · 무적 · 관통 · 시전 중 …을 각각 필드로 두면 “스턴이면서 무적”이 유효한지를 코드 여기저기의 if 조합이 암묵적으로 결정합니다. 태그를 지속 시간과 함께 붙였다 떼는 방식으로 바꿨습니다.
  • 상태를 읽는 곳을 관문 셋으로 모았습니다 — CanMove · CanAttack · CanUseSkill, 곧 움직여도 되나 · 때려도 되나 · 스킬 써도 되나를 묻는 자리 셋입니다. 상태를 읽는 곳이 흩어지면 새 태그를 추가할 때 빠뜨리는 곳이 생깁니다. 지금은 새 상태이상 = 태그 이름 하나 + 게이트 한 줄이고, 데이터가 태그 이름을 문자열로 그대로 갖고 있어서 코드 변경 없이 스킬에 붙습니다.
  • 태그로 표현하면 안 되는 것을 갈랐습니다. 태그는 “남이 나에게 건 것”입니다. 그런데 스킬에는 “내 스킬이 나를 잠깐 다른 상태로 만든 것”이 있습니다 — 돌진 중 관통, 체공 중 무적, 소울실드의 피해 배율 같은 것들. 이걸 태그로 두면 “적이 나에게 무적을 걸 수 있다”는 이상한 구조가 됩니다. 그래서 상태이상은 피격자가, 시전 상태는 시전자가 소유하고 컨트롤러는 질의로만 읽습니다.
  • 수치는 3층으로 뺐습니다 — 전투 콘텐츠 CSV 5종(캐릭터·무기·직업·스킬·유물 — 기획자가 고치는 표. 이후 성장 시스템 표가 붙어 조회 창구가 다루는 표는 지금 9종) → 조회 창구 하나(그 표를 읽는 유일한 문) → 스탯 합성(읽은 값들을 하나로 더하고 곱하는 자리). CSV 칸은 전부 글자라, 읽는 쪽마다 숫자로 바꾸면 “값이 비었을 때 뭘 쓸지”가 여기저기 흩어집니다. 글자 → 숫자 변환을 한 곳에서 끝냈습니다.
  • 어휘를 미리 맞춰 변환 계층을 없앴습니다. 스킬 데이터의 넉백 등급과 상태 태그가 인프라가 받는 어휘를 그대로 씁니다 (low/mid/high, Stun/Silence/Immobile). CSV 셀을 읽어 그대로 넘기면 됩니다. 인프라를 스킬보다 먼저 만들었기 때문에 가능했습니다 — 순서가 반대였다면 스킬마다 자기 어휘를 만들고 나중에 매핑 표가 생겼을 것입니다.
  • 직업은 스탯을 주지 않습니다. 직업 데이터에 스탯 컬럼이 없습니다 — “스탯은 전부 무기가 결정한다”는 기획 원칙이라, 직업은 시그니처 무기와 고유 스킬 하나로만 정의됩니다. 당시 캐릭터 데이터가 스탯을 갖고 있었지만 무기 담당 영역이라 건드리지 않고 커밋 메시지에 남겼습니다.

화면

어려움

문제
스킬을 붙이려고 상태 컴포넌트를 다시 열어보니 추가 · 조회 · 틱 · 정리가 전부 구현돼 있는데 태그를 붙이면 영원히 안 풀리는 상태였습니다.
원인
이 컴포넌트는 프로젝트 초기에 만들어 둔 것이고, 틱을 부르던 드라이버가 기능 01의 이관에서 은퇴하면서 아무도 안 굴리고 있었습니다. 아무도 태그를 쓰지 않아서 증상이 드러나지 않았을 뿐입니다. 마이그레이션에서 “삭제 목록”은 챙겼지만 “삭제된 것이 부르던 것” 목록은 안 챙긴 것입니다.
해결
서버 틱에 연결했습니다. 고치는 것 자체는 한 줄이었지만, 이 종류의 실패는 에러를 내지 않는다는 걸 여기서 배웠습니다. 이후 “조용히 죽는 배선”에는 존재 확인 로그를 심는 습관이 생겼고, 같은 형태의 문제를 기능 05에서 다시 만났을 때 훨씬 빨리 잡았습니다.

성과

스킬 8종을 붙이며 인프라 호출부 0줄 수정 드라이버에 박혀 있던 하드코딩 상수 4종 제거 아레나 경계를 맵에서 읽어 새 맵이 코드 수정 없이 반영
기능 04

유물 52종 — 데코레이터를 기각하고 애그리게이터로

패턴을 고르고 요구사항을 맞춘 게 아니라, 요구사항을 적었더니 패턴이 나왔습니다. 데코레이터는 효과를 겹겹이 감싸는 방식, 애그리게이터는 전부 한 표에 모아 수식 한 줄로 합치는 방식입니다.

구현

  • 요구사항을 먼저 네 줄로 적었습니다. 획득 순서가 매 판 랜덤 → 순서 독립적인 합성. 상한 없이 15개까지 누적 → 무제한 중첩. 라운드 단위로 소멸하는 것이 섞임 → 범위별 일괄 제거. 종류가 계속 늘어남(52 → ?) → 유물 추가 = 데이터 추가. 이 네 줄이 이후 판단을 사실상 다 결정했습니다.
  • 착수 전에 붙일 자리를 조사했더니 스탯 경로가 이미 두 갈래였습니다. 정상 경로(기본값 + 덧붙는 수치 조각 모디파이어)와, 스킬이 자기 버프 표를 따로 만든 우회 경로. 우회가 생긴 이유는 공격속도가 스탯으로 존재하지 않았기 때문입니다 — 저장할 자리가 없으니 스킬 쪽에서 테이블을 만든 것이고, 그 결과 중첩이 안 되고(슬롯 하나를 통째로 덮어씀) 지속시간 관리가 따로 놀았습니다.
  • 그래서 구현 순서 1~2번을 유물이 아니라 통합 작업으로 잡았습니다. 유물 하나 못 만든 상태에서 기존 스킬 코드를 먼저 건드리는, 겉보기엔 이상한 순서입니다. 근거는 비용의 시점 차이였습니다 — 지금 하면 위임 메서드 세 개의 내부만 갈아끼우고 호출부는 한 글자도 안 바뀝니다. 나중에 하면 양쪽 호출부를 전부 조사해야 하고, 그 사이에 “이 버프가 어느 쪽에서 오는가”가 코드에 굳습니다.
  • 스킬 버프가 모디파이어가 되면 중첩이 자동으로 성립합니다. 유물 · 스킬 · 무기가 같은 표에 모이므로 별도 중첩 로직이 필요 없습니다.

왜 데코레이터가 아닌가 — 기각 사유 넷

  • ① 감쌀 대상이 없습니다. 52종을 성격별로 세어보니 순수 스탯 18 · 조건부 트리거 18 · 무기 고유 16이었습니다. 데코레이터가 감쌀 수 있는 건 순수 스탯 18종뿐이고 나머지 34종은 트리거입니다. 가장 명확한 반례가 “적중 시 적의 이동속도 -5%” — 이건 내 스탯 계산을 감싸는 게 아니라 남의 스탯에 모디파이어를 거는 핸들러입니다. 데코레이터는 내 호출을 가로채는 패턴인데, 여기엔 가로챌 내 호출이 없습니다.
  • ② 순서 독립성이 밸런스 요구사항입니다 (결정타). 체인은 감싼 순서가 곧 연산 순서입니다. 획득 순서가 매 판 랜덤이므로 같은 유물 조합을 든 두 플레이어의 수치가 달라집니다. 이 버그는 에러가 안 나고, 재현 조건이 “특정 순서로 먹었을 때”라 추적이 어렵고, 밸런스 테스트 결과 자체를 신뢰할 수 없게 만듭니다. 체인으로도 “항상 고정값을 안쪽에 두자”는 규칙을 세울 순 있지만 그건 컴파일러가 검사해주지 않는 관례라 종류가 늘면 반드시 깨집니다.
  • ③ 제거가 비싸고, 하필 그 경로가 뜨겁습니다. 라운드 종료 시 초기화되는 유물이 5종인데, 배열이면 필터 한 번이고 체인이면 20겹 중간의 노드를 동일성으로 찾아 빼고 앞뒤를 다시 잇는 사실상 재구성입니다. 게다가 스탯 조회는 이동·전투에서 프레임마다 도는 경로입니다 — 체인 20겹이면 조회 한 번에 간접 호출 20회입니다.
  • ④ 플랫폼에 맞지 않습니다. 이 언어에는 인터페이스도 제네릭도 없고, 스크립트 하나가 파일 쌍 + 에디터 등록을 뜻합니다. 52쌍은 관리 불가입니다. 클로저 테이블로 만들 수도 있지만 그러면 그건 이미 데코레이터가 아니라 핸들러 표입니다 — 패턴 이름만 남고 실체는 사라집니다.
  • 그리고 패턴의 존재 이유 자체가 성립하지 않았습니다. 데코레이터는 수정할 수 없는 클래스에 행동을 덧붙이는 우회로입니다 — 남의 라이브러리, 다른 팀 소유 코드, 상속이 봉인된 클래스. 그런데 스탯 컴포넌트는 우리 코드 270줄이고 확장점이 이미 뚫려 있었습니다. 있는 문을 두고 벽을 뚫는 셈이었습니다.

성과

유물 획득 순서와 무관하게 같은 조합 = 같은 수치 새 패턴 도입 0 — 깔아둔 애그리게이터를 가동시키고 트리거 한 겹만 추가 스탯 경로 3갈래로 늘어날 뻔한 것을 1갈래로 수렴

공정하게 적자면 무기 고유 16종은 성격이 다릅니다 — 스탯이 아니라 공격 행동 자체를 변형하므로 “기존 공격 → 공격 + 투사체”는 개념적으로 데코레이션에 가깝습니다. 다만 ④의 플랫폼 제약이 그대로 살아 있어서 실제로는 메커니즘 슬러그(효과 종류를 가리키는 짧은 이름표) 표로 갈라 처리하는 편이 낫다고 판단했습니다.

기능 05

플레이어가 만지는 것 — 유물 · 스킬 · 어빌리티를 한 표에 모으기

데이터를 먼저 세었더니 핸들러가 52개가 아니라 6개였습니다.

구현

  • 핸들러 표는 52행이 아니라 6행입니다. 트리거가 “획득 / 라운드 종료 / 승리 / 패배” 중 하나이고 효과 키가 채워져 있으면 공통 코드 한 줄로 끝납니다. 그래서 전체의 35%가 CSV 행 추가만으로 늘어납니다. 52종을 세기 전에는 “핸들러 52개”를 상상했는데, 세고 나니 6개였습니다.
  • 기획 어휘와 코드 어휘를 표 하나로 이었습니다. CSV의 효과 키는 기획자가 쓰는 말(damage, atk_spd)이고 스탯 키는 코드가 쓰는 말(AttackPower, AttackSpeedRate)입니다. 기능 03에서는 어휘를 아예 일치시켜 변환을 없앴지만, 이번엔 원본 스프레드시트를 기획자가 소유하므로 그 방법을 못 씁니다. 대신 변환 지점을 한 곳에 못 박았습니다 — 흩어진 변환이 문제지 변환 자체가 문제는 아닙니다.
  • 소멸 시점을 데이터로 뺐습니다 (범위 3단). 매치 종료까지 남는 것 / 라운드 종료에 지워지는 누적형 5종 / 몇 초 뒤 자동 소멸하는 것. 마지막 칸은 유물 요구사항이 아니라 스킬 버프를 흡수하려니 필요해진 칸입니다.
  • 유물은 가산, 스킬 버프는 곱연산으로 갈랐습니다. 기획서에 없어서 스스로 정한 규칙입니다. 15라운드 × 상한 없음이라 곱연산은 후반에 지수로 폭주합니다. 대신 짧고 독립적인 스킬 버프만 곱으로 두면 스킬의 상대적 가치가 유물 누적량과 무관하게 유지됩니다 — 가산이었다면 후반에 “공속 +10%”가 전체의 3%가 되어 스킬이 무의미해집니다. 별도 코드나 예외 처리 없이 연산자 선택만으로 두 시스템의 성질이 갈립니다.
  • 훅은 새로 파지 않고 기존 지점을 승격했습니다. 트리거 붙일 자리를 조사했더니 대부분 이미 있었습니다. 특히 방향 전환은 관문이 하나뿐이라 그 한 줄에 유물 5종이 전부 걸립니다 — 기능 01에서 권위를 한 곳으로 모은 것이 여기서 배당금을 냈습니다. 권위가 흩어져 있었다면 훅을 다섯 군데에 심어야 했습니다.
  • 밸런스는 혼자 정하지 않았습니다. 기획 수치의 내적 모순을 발견했을 때 임의로 고치지 않고 선택지 셋과 각각의 대가를 정리해 결정을 요청했습니다. 반대로 구조 결정(중첩을 가산으로 할지 곱으로 할지)은 지금 정하지 않으면 진행이 막히므로 근거를 명시하고 스스로 정했습니다. 수치면 물어보고, 구조면 정하고 적는다가 기준이었습니다.

문제
훅 핸들러 다섯 개가 직접 호출하면 정상 동작하는데 실전에서는 한 번도 불리지 않고 있었습니다. 같은 모양의 버그를 하루에 두 번 만났습니다.
원인
두 가지가 겹쳤습니다. 하나는 관문을 잘못 짚은 것 — 처음 잡은 함수는 서버와 클라 양쪽에서 도는 것이라 두 번 발동했고, 그래서 서버 전용 함수로 좁혔더니 그 함수에 도달하는 경로가 이미 0개였습니다(봇을 걷어내며 호출부가 사라짐). 다른 하나는 코드가 갈라지는 축(서버/클라 · 근접/원거리)에서 한쪽 분기에만 호출부를 둔 것입니다. 근본은 “핸들러가 도는가”만 확인하고 “실전에서 그게 불리는가”를 봤다고 착각한 것입니다.
해결
진짜 관문을 찾아 한 줄로 고쳤습니다. 더 값이 컸던 건 절차 쪽입니다 — “동작한다”를 두 층으로 나눠 묻기로 했습니다. 핸들러가 도는가, 그리고 실전 경로가 그것을 부르는가. 그리고 이 두 건은 게임을 띄우기 전에 검색 한 번으로 보였을 문제였습니다. 실측을 늘리는 것보다 실측 이전에 할 수 있는 정적 확인을 빠뜨리지 않는 쪽이 값이 컸습니다.

성과

핸들러 6행으로 52종 처리 — 전체의 35%는 CSV 행 추가만으로 증가 기획 어휘 ↔ 코드 어휘 변환 지점 1곳 유물·스킬·무기가 같은 표에 모여 중첩 로직 별도 구현 0

미리 세운 인터페이스에 대해 — 3주 전에 사용처가 하나도 없는 상태로 모디파이어 인터페이스를 먼저 깔아뒀고, 유물이 들어올 때 순수 스탯 18종이 새 코드 없이 그대로 얹혔습니다. 다만 정직하게 적자면 미리 세운 인터페이스는 “맞았다”가 아니라 “아직 안 틀렸다”에 가깝습니다 — 첫 호출부가 붙는 순간이 실제 검증 시점이고, 그래서 구현 순서에서 검증 항목을 “조회 값 전후 비교 로그”로 잡았습니다.

기능 06

타격 판정을 “닿는 순간”으로 — 그리고 내 설계를 데이터로 반박

공격하는 일과 맞는 일을 분리했더니 회피가 성립했고, 관대하게 만들려고 넣은 기능은 재보니 거의 일하지 않았습니다.

구현

  • 한 함수였던 공격을 둘로 갈랐습니다 — 스윙은 쿨 소모와 모션만(적이 있든 없든 실행), 판정은 무기별 지연 뒤에. 판정 시점에 그때의 위치와 방향으로 대상을 다시 찾습니다. 스윙 시작 때 찾아둔 대상을 기억하지 않습니다. 그래서 대시로 빠져나가면 맞지 않습니다.
  • 무기마다 판정 지연을 뒀습니다 — 주먹·대검 0.5 / 둔기 0.35 / 활 0.25. 무기가 실제로 닿는 순간이 모션마다 다르므로 값도 무기별로 다릅니다.
  • 지연은 한 점이라 그 순간 그 자리에 없으면 무조건 빗나갑니다. 격투게임의 액티브 프레임처럼 판정이 열려 있는 구간을 줬습니다 — 대검 0.18 / 둔기 0.16 / 주먹·표창·스태프·활 0.10 / 단검·너클 0.08 / 권총 0.06. 무거울수록 관대, 빠를수록 좁게가 배분 규칙입니다.
  • 다단히트가 아닙니다 — 적중하면 구간을 즉시 닫습니다. 안 닫으면 한 스윙이 10회 이상 때립니다.

기능 07

협업 경계 — 1511줄을 셋으로

파일이 길어서 나눈 것이 아니라, 두 사람의 손이 한 파일에서 겹쳐서 나눴습니다.

구현

  • 컨트롤러 한 파일을 컴포넌트 셋으로 갈랐습니다 — 공용 714줄(파이터 상태 권위 + 이동/밀림 + 공개 API), 무기 300줄, 스킬 470줄. (분리 커밋 시점 · 주석·공백을 뺀 실동 코드 기준)
  • 기준은 줄 수가 아니라 공유 상태 의존도였습니다. 컨트롤러가 파이터 위치·방향의 유일한 주인으로 남습니다 — 동기화 프로퍼티라 다른 스크립트가 쓸 수 없고, 전투·스킬은 공개 동사로만 파이터에 닿습니다.
  • 경계를 API 계약 문서에 먼저 쓰고, 그다음에 코드를 옮겼습니다. 각자 자기 구역을 옮기는 동안 서로 무엇을 부를 수 있는지가 이미 정해져 있었습니다.
  • 형제 컴포넌트는 필요할 때 찾습니다. 초기화 순서가 보장되지 않아 시작 시점에 캐시하면 한쪽이 아직 없을 수 있습니다.
  • 조용히 죽는 배선에 경고를 심었습니다. 새 아레나 맵에 컴포넌트 셋 중 하나를 안 붙이면 에러 없이 그 기능만 사라집니다. 형제 존재 확인 로그를 넣었습니다.

성과

같은 파일을 만지던 둘이 각자 자기 컴포넌트로 분리 분리 후 2인 실측 2판 · 에러 0 · 훅 전부 생존 확인 배선 누락에 경고 — 조용히 죽지 않게

범위와 한계

4인 팀이며 제 담당은 플레이어 이동 · 전투 · 스킬 · 유물 시스템, 데이터 레이어, 서버 권위 구조입니다. 초기 서버 권위 이동 프로토타입과 플레이어 충돌·애니메이션 동기화는 팀원(PR #1), 스킬 키 UI 그룹은 다른 팀원(PR #2), 매치메이킹은 별도 담당입니다. 멀티 담당자와는 초기에 폴더로 완전히 분리해 작업했고(머지 시 충돌 0건), 이후 서버 컨트롤러가 공통 기반이 되면서 같은 파일을 만지게 되자 기능 07로 경계를 다시 세웠습니다.

진행 중인 프로젝트입니다. 위 일곱 기능은 구현과 검증이 끝났고, 스킬·무기 강화 등 콘텐츠 볼륨과 밸런스가 9월 중순까지 남아 있습니다. 수치와 구조는 그 과정에서 바뀔 수 있습니다.

측정 방식 — MSW Maker MCP로 에디터를 자동 조작했습니다 (refresh → play → 서버 컨텍스트에 스크립트 주입 → 로그 수집 → stop). 원칙 두 가지를 지켰습니다 — 런타임 주장에는 반드시 실행 결과를 붙인다, 그리고 멀티플레이 기능은 원격 대상으로 측정한다. 두 번째는 기능 02에서 크게 오진하고 나서 세운 것입니다.

남아 있는 것도 적어둡니다 — 상태 태그가 서버 사본에만 있어 HUD에 버프/디버프 아이콘을 띄우려면 동기화 수단이 필요하고, 틱이 실제 경과 시간이 아니라 고정값이라 프레임이 떨어지면 게임 전체가 함께 느려집니다. 상대 밸런스는 유지되지만 구조적 한계라 문서에 남겨뒀습니다.
