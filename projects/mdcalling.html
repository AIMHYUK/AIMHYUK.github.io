1. 테트리스형 2D 그리드 인벤토리
  • InventoryModel이 InventoryItem[,] _grid 2D 배열로 상태를 관리, 이벤트(OnItemPlaced / OnItemRemoved)로 View에 통보하는 이벤트 기반 MVC 패턴 설계
  • 아이템마다 InventorySize(Vector2Int)와 IsRotated 플래그를 두어 90도 회전 시 EffectiveSize의 x/y를 교환 — 배치 충돌 판정에 그대로 반영
  • TryPlace / CanPlace 메서드가 차지하는 모든 셀을 순회해 공간 충돌을 원자적으로 검사
  • OutsideInventoryAreaView로 그리드 밖 좌·우 인벤토리 영역을 독립 관리 — 그리드 경계에서 방향키 입력 시 Outside 영역으로 포커스 자동 전환
  • InventoryDragPreviewView가 드래그 중 아이템 실루엣과 배치 가능 여부 하이라이트를 실시간 렌더링
  • 구현 — InventoryModel이 2D 배열로 점유 상태를 관리하고, 아이템 배치 전 모든 점유 셀을 검사해 원자적으로 배치했습니다. 회전 상태는 EffectiveSize로 계산해 충돌 판정에 반영했습니다.
  • 결과 — 아이템 크기와 회전 상태를 반영한 테트리스형 인벤토리를 만들고, Model 이벤트를 통해 UI가 상태 변경을 구독하는 구조로 분리했습니다.
// 실제 구현 요약 - 모든 점유 셀을 검사한 뒤 한 번에 배치
public bool CanPlaceSize(int width, int height, Vector2Int position)
{
    for (int x = position.x; x < position.x + width; x++)
    {
        for (int y = position.y; y < position.y + height; y++)
        {
            if (!IsInBounds(x, y)) return false;
            if (_grid[x, y] != null) return false;
        }
    }
    return true;
}

public bool TryPlace(InventoryItem item, Vector2Int position)
{
    if (!CanPlace(item, position)) return false;

    int width = item.EffectiveSize.x;
    int height = item.EffectiveSize.y;
    for (int x = position.x; x < position.x + width; x++)
    {
        for (int y = position.y; y < position.y + height; y++)
            _grid[x, y] = item;
    }

    item.Place(position);
    _placedItems.Add(item);
    RecalculateTorque();
    OnItemPlaced?.Invoke(item, position);
    OnTorqueChanged?.Invoke(CurrentTorque);
    return true;
}

2. 마우스 · 게임패드 하이브리드 입력 (InventoryState)
  • Mouse.current.delta.sqrMagnitude > 0.1f 감지로 마우스 모드 전환, 게임패드 버튼 입력 시 패드 모드로 즉시 전환 — 하나의 인벤토리가 두 입력장치를 실시간 병행 지원
  • 스틱 아날로그 입력을 디지털 4방향으로 변환하고 초기 딜레이(0.4s) + 반복 간격(0.12s) 타이머로 키 반복 네비게이션 구현
  • 그리드 좌·우 경계에서 방향 입력 시 Outside 영역으로, 반대 방향 입력 시 그리드 가장자리 셀로 포커스 자동 이동하는 스마트 네비게이션
  • 패드 A 버튼 — 토글 방식으로 집기·놓기, LB/RB — 드래그 중 아이템 90도 회전, B 버튼 — 드래그 취소 및 원위치 복구
  • 결과 — 같은 인벤토리 UI를 마우스와 게임패드 양쪽에서 사용할 수 있게 만들어, 입력 장치가 바뀌어도 플레이 흐름이 끊기지 않도록 했습니다.
3. 장소 기반 퀘스트 시스템
인스펙터 데이터 구조 — 코드 수정 없이 데이터만 바꿔 새 퀘스트 제작 가능
Quest (ScriptableObject)
├─ TaskGroup[0]
│   ├─ QuestTask  category: "DELIVERY_ACCEPT"  target: A장소
│   └─ QuestAction  → Yarn 대화 노드 변경
└─ TaskGroup[1]
    └─ QuestTask  category: "DELIVERY_COMPLETE"  target: B장소
설계 의도
  • DeliveryManager는 퀘스트를 직접 알지 않고 "DELIVERY_ACCEPT", "DELIVERY_COMPLETE" 같은 진행 이벤트만 QuestManager에 보고하도록 분리했습니다.
  • QuestManager는 활성 퀘스트 전체에 보고를 broadcast하고, 각 QuestTask가 category + target 조합으로 자신에게 해당하는 진행인지 판단합니다.
  • TaskGroup 완료 시 QuestAction을 실행해 배달 요청 생성, 보상, 장소별 yarnStartNode 변경 같은 후속 처리를 데이터 기반으로 연결했습니다.
낮은 결합도

배달 시스템은 배달 상태만 관리하고, 퀘스트 시스템은 보고된 이벤트만 해석합니다.

데이터 기반 확장

새 퀘스트는 코드 수정 없이 TaskGroup, category, target, action 조합으로 추가할 수 있습니다.

대화 진행도 반영

퀘스트 진행에 따라 장소의 Yarn 시작 노드를 바꿔 같은 장소에서도 다른 대화를 시작합니다.

런타임 흐름
1
Yarn에서 퀘스트 지급 <<give_quest>>
2
퀘스트 등록 QuestManager.Register
3
배달 요청 생성 DeliveryGiveQuestAction
4
수락/완료 보고 ReceiveReport
5
TaskGroup 완료 QuestAction 실행
6
대화 노드 변경 SetYarnStartNode
마지막 TaskGroup에서는 그룹 완료 액션이 먼저 실행되고, 이후 useAutoComplete 설정에 따라 퀘스트가 완료됩니다. 따라서 yarnStartNode 변경은 “퀘스트 완료 후”가 아니라 “TaskGroup 완료 시점”에 일어납니다.
  • 구현 — 배달 시스템은 퀘스트를 직접 참조하지 않고 category + target 형태의 진행 이벤트만 보고합니다. QuestManager는 활성 퀘스트에 broadcast하고, 각 QuestTask가 자신에게 맞는 이벤트인지 판단합니다.
  • 결과 — 배달, 대화, 퀘스트 진행을 느슨하게 연결해 새 배달 퀘스트를 데이터 조합으로 추가할 수 있게 만들었습니다.
// 실제 구현 요약 - 시스템 간 직접 참조 대신 category + target 이벤트로 진행 보고
public bool IsTarget(string categoryStr, IdentifiedObject target)
    => HasCategory(categoryStr)
    && targets.Any(x => x.IsSameAs(target))
    && IsComplete == false;

public void ReceiveReport(string category, IdentifiedObject target, int count)
{
    foreach (var quest in _activeQuests.ToArray())
        quest.ReceiveReport(category, target, count);
}

회고 및 개선 방향
  • 문제 — 인벤토리와 퀘스트 모두 데이터 중심으로 확장 가능하게 만들었지만, 문자열 category와 복잡한 UI 포커스 규칙은 규모가 커질수록 오류 가능성이 있습니다.
